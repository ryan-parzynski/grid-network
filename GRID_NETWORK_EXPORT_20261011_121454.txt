## Integration Pattern

Applications integrate with the local Grid agent via a small API:

```
grid.connect(service_link_id, capability) → local connection handle
grid.resolve(peer_id)                     → peer state
grid.discover()                            → list of known peers
grid.revoke(object_id)                     → issue revocation
grid.status()                              → daemon state
```

The application calls `grid.connect` with the service it wants to reach and the capability it wants to exercise. The agent returns a local URL. The application treats that URL like any other local service.

# Grid Network — Commercial Model

## Executive Summary

Grid Network's commercial model exists to fund the protocol's maintenance, not to extract value from users. Every participant — free user, contributor, commercial operator, enterprise — makes the network more valuable to every other participant.

**Core principle:** Free tier is real. Paid tier gets priority, not access.

---

## 1. Tier Structure

### Free Tier (Best-Effort)
- Unlimited relay usage (subject to fair-share limits)
- Unlimited rendezvous queries
- Full protocol features
- No account required
- No payment information
- Limits: Fair-share bandwidth (e.g., 1 Mbps concurrent, 10 GB/month), best-effort relay priority, rate limits on rendezvous queries

### Standard Tier ($5-10/month)
- 10 Mbps minimum relay bandwidth (guaranteed)
- Priority queuing (after dedicated, before free)
- Higher rate limits (30 lookups/sec)
- SLA: 99% uptime (monthly)

### Priority Tier ($20-50/month)
- 50 Mbps minimum relay bandwidth
- Highest priority queuing
- Lowest latency routing
- SLA: 99.5% uptime + latency <100ms

### Dedicated Tier (Custom Pricing)
- Guaranteed capacity (custom per agreement)
- Private relay if desired
- Highest priority (always served first)
- SLA: 99.99% uptime + custom latency guarantees
- 24/7 support
- Custom integration

---

## 2. Idle Capacity Donation

When paid users don't use reserved capacity, it flows to free pool.

```
Relay capacity: 100 Gbps total

Allocation:
  Free users: 20 Gbps (first-come-first-served)
  Standard: 40 Gbps (reserved)
  Priority: 30 Gbps (reserved)
  Dedicated: 10 Gbps (reserved per customer)

During peak evening:
  Standard users using 35 Gbps (5 Gbps idle)
  Priority users using 25 Gbps (5 Gbps idle)
  Idle capacity: 10 Gbps

Free users get: 20 Gbps reserved + 10 Gbps idle = 30 Gbps available
```

This model ensures free users have bandwidth, doesn't penalize paid users, and encourages overprovisioning.

---

## 3. Credit System

Users earn credits by contribution and spend on relay usage.

### Contribution
- Running a relay: earn per byte relayed
- Running a rendezvous: earn per query served
- Sharing reachability: earn per connected hour

### Exchange Rate
- 1 credit = 1 GB of relay bandwidth (standard tier)
- Scarcity multiplier for scarce regions

### Example
- Alice runs Pi relay for 1 month → relays 100 GB → earns 100 credits
- Spends 50 credits on her own relay usage
- Remaining: 50 credits (carry over)

### Fair Exchange
User invests $2 electricity → gets 100 credits → spends 100 credits → gets $100 of relay service. User profits on investment!

---

## 4. Credit Pools

Users can share relay credits in pools (families, groups).

```
Alice's family pool:
  Alice: $10/month
  Bob: $10/month
  Charlie: $5/month
  Total: $25/month = 2500 credits
  Shared among: Alice's server, Bob's server, Charlie's phone
```

Rules:
- Credits allocated to a pool
- Pool operators manage distribution
- Credits don't transfer between pools (prevents laundering)
- Credits are account-specific (can't be sold)

---

## 5. Geographic Scarcity & Fairness

Problem: Some regions have many relays, others have few.

Solution: Geographic multiplier.

```
Relay in NYC (abundant): 1 credit per GB
Relay in rural Iowa: 3 credits per GB
Relay in remote region: 5+ credits per GB
```

Multiplier calculated monthly from demand/supply ratio. Incentivizes operators to deploy in underserved areas.

---

## 6. Developer Funding

Commercial operators contribute 20% of revenue to developer fund.

```
Relay operator revenue: $100,000/month
Distribution:
  Operator: $80,000
  Developer fund: $20,000
  Infrastructure cost: $50,000 (paid from $80k)
  Operator margin: $30,000
```

Developer fund (20%) covers:
- Protocol maintenance
- Specification work
- Test vector production
- Security audits
- Documentation
- Community support

Why structural revenue share? Donations/grants are unreliable. Revenue share scales with adoption and incentivizes operators to grow the network.

---

## 7. Stewardship Entity

Independent of any commercial operator. Responsibilities:
- Maintain protocol specification
- Produce test vectors
- Conduct security audits
- Manage RFC process
- Arbitrate disputes

Funded by 20% revenue share from all operators. Board elected by operators + users. Prevents commercial capture.

---

## 8. What Commercial Operators Sell

**Operators do NOT sell:**
- Access to the network (it's open)
- Device identity (owned by user)
- Relationship data (on user's device)
- Authorization grants (signed by user)

**Operators DO sell:**
1. Reliability — Guaranteed uptime/latency SLA
2. Bandwidth — Reserved relay capacity
3. Geographic placement — Relays near the user
4. Support — Responsive help when things break
5. Integration — Custom setups for enterprises
6. Compliance — Audit logs, HIPAA/FedRAMP/SOC2 support

---

## 9. Economic Shape (The Flywheel)

```
Free users create network effect
  ↓
Developers see value, integrate Grid
  ↓
Applications adopt Grid
  ↓
Users get connectivity automatically
  ↓
More users (free) = bigger network
  ↓
Enterprises need better SLA
  ↓
Enterprises pay for premium tiers
  ↓
Commercial operators run relays
  ↓
Operators fund developer work

```

## 10. Commercial Disruption

If Grid Network succeeds:

**Today's market:**
- Tailscale: owns device graph, $39.95/month per user
- Cloudflare Tunnel: $180/month for enterprise
- ZeroTier: free tier + $99/month for central management

**Post-Grid market:**
- Device graph: free (commoditized, Grid layer)

What changes:
- Vendors can no longer charge for "device identity"
- Competition moves from "lock-in" to "quality"
- Smaller operators can enter market
- Users can switch providers without losing relationships

What survives:
- Vendors that are genuinely excellent
- Enterprise integration (custom configs, support)
- Hardware appliances (routers with Grid built-in)
- Managed infrastructure (users who don't want to self-host)

# Part A — Cryptographic Constructions in Full

## A.1 The four representations of an object

An object in Grid Network passes through four distinct representations before it becomes a wire-format artifact. Confusing them is the single most common source of implementation bugs, so they are named explicitly:

```
1. unsigned_payload
       │
       │ (canonical CBOR, with tag string)
       ▼
2. commitment_preimage
       │
       │ (SHA-256)
       ▼
3. object_commitment
       │
       │ (combined with previous_chain_hash)
       ▼
4. chain_hash
       │
       │ (combined with tag, unsigned_payload, chain_hash)
       ▼
5. signature_input → signature
       │
       │ (added to unsigned_payload along with chain_hash)
       ▼
6. signed_object_bytes
```

Every step is deterministic. Given any unsigned_payload and the stream state, all downstream values are fully determined.

## A.2 Commitment preimage and object commitment

```
commitment_preimage =
    canonical_cbor([
        "grid/commitment/v1",
        domain_separator,
        unsigned_payload
    ])

object_commitment =
    SHA-256(commitment_preimage)
```

The tag string `"grid/commitment/v1"` is part of the preimage. This is what makes the commitment domain-separated from every other hash the protocol computes. Two objects with identical content but different domain separators produce different commitments.

`object_commitment` is the value that appears in the *next* object's `previous_hash` field.

## A.3 Chain base and chain hash

The chain base is bound to the specific stream, not just to the object type:

```
initial_chain_hash =
    SHA-256(canonical_cbor([
        "grid/chain-base/v1",
        domain_separator,
        stream_id
    ]))
```

This ensures that two distinct streams of the same object type cannot share an initial chain hash by accident.

The chain hash for the first object uses the chain base as the predecessor:

```
previous_chain_hash(1) = initial_chain_hash
previous_chain_hash(N) = chain_hash(N-1)          for N > 1

chain_hash(N) =
    SHA-256(canonical_cbor([
        "grid/chain/v1",
        previous_chain_hash(N),
        object_commitment(N)
    ]))
```

The chain hash commits to the entire presented prefix of the stream. It does not by itself reveal unseen siblings. Fork detection requires eligible authenticated conflicting evidence — the verifier must receive and verify two objects at the same sequence number with different object commitments (or their chain hashes) to know a fork occurred.

**Fork evidence walkthrough.** Suppose the issuer produces two conflicting objects at sequence 3:

```
Branch A:
  seq 1 (commitment: c1, chain: h1)
  seq 2 (commitment: c2, chain: h2 = F(h1, c2))
  seq 3 (commitment: c3, chain: h3 = F(h2, c3))

Branch B:
  seq 1 (commitment: c1, chain: h1)
  seq 2 (commitment: c2, chain: h2 = F(h1, c2))
  seq 3 (commitment: c3', chain: h3' = F(h2, c3'))
```

A verifier that has accepted sequence 2 holds `chain_hash = h2`. When it receives a sequence-3 object, it recomputes `F(h2, c3)` and compares to the object's stated `chain_hash`. If they match, the object extends the accepted chain. If the verifier later receives a *different* sequence-3 object (from branch B) with commitment `c3'` and chain hash `h3'`, it can compare the two commitments at the same sequence position. The conflict `c3 != c3'` (or equivalently `h3 != h3'` with the same predecessor `h2`) is the authenticated evidence of a fork. Without seeing both branches, the verifier cannot distinguish between a valid extension and a forked branch — the chain hash only commits to the prefix it has seen.

The "Fork detection walkthrough" in MODEL.md Part A.3 is replaced by the "Fork evidence walkthrough" above. The key correction: a verifier with only one branch's sequence-3 object accepts it as a valid chain extension. Fork detection occurs only when the verifier later receives an eligible authenticated conflicting object at the same sequence number from a different branch. The cumulative hash commits to the presented prefix; it does not reveal unseen siblings.
## A.4 Payload ID and object ID

Two identifiers serve different purposes.

```
payload_id =
    SHA-256(canonical_cbor([
        "grid/payload-id/v1",
        unsigned_payload
    ]))

object_id =
    SHA-256(canonical_cbor([
        "grid/object-id/v1",
        canonical_signed_object_bytes
    ]))
```

`payload_id` identifies the semantic content. It is computed before the signature and is one of the inputs to the signature. Two objects that mean the same thing have the same payload_id.

`object_id` identifies the specific signed artifact. It is computed after the signature. Two objects with identical payloads but different signatures (for example, signed by different keys) have different object_ids.

**Why the distinction matters.** A grant revocation must reference *the specific signed grant* it revokes, not "a grant that means roughly the same thing." So revocations carry `object_id`. But if a verifier wants to determine whether two revocation records are about the same underlying grant, it compares payload_ids. Having both lets the protocol express both relationships.

## A.5 Signature input and signature

```
signature_input(N) =
    canonical_cbor([
        "grid/signature/v1",
        domain_separator,
        unsigned_payload(N),
        chain_hash(N)
    ])

signature(N) =
    Ed25519_sign(signing_private_key, signature_input(N))
```

The signature covers the *unsigned payload directly*, not its hash. This is deliberate. If the signature covered the payload hash, an attacker who could produce a hash collision could substitute a different payload for the same signature. Signing the payload itself (within a canonical CBOR framing) removes that attack.

The `chain_hash` is included in the signature input, so the signature commits to the entire stream history as well as to the current object's content.

**Non-circularity.** The signature is not part of its own input. The `chain_hash` is derived from the unsigned payload and the stream state; the signature is derived from the `chain_hash` and the unsigned payload. There is no cycle.

# Part B — Verification Procedure in Full

## B.1 The ten steps

A verifier processes a candidate object in this order. Each step has a specific rejection class.

**Step 1 — Parse.** Decode the bytes as CBOR according to the canonical profile. Reject as `MALFORMED_ENCODING` if the bytes are not valid CBOR or violate any canonical-form rule.

**Step 2 — Envelope validation.** Verify that the object contains `domain_separator`, `sequence`, `previous_hash` (omitted at sequence 1), `chain_hash`, and `signature` as text/byte strings of the correct types. Reject as `MALFORMED_ENVELOPE` if any required field is missing, mistyped, or if any unknown top-level field is present.

**Step 3 — Domain separator validation.** Verify that the `domain_separator` is in the registered set. Reject as `UNKNOWN_SCHEMA` if the value is not registered.

**Step 4 — Schema validation.** Validate the object's schema-specific fields according to the object type's schema definition. Reject as `MALFORMED_SCHEMA` if any field fails validation.

**Step 5 — Sequence validation.** Verify that `sequence >= 1`. Verify that `previous_hash` is present if and only if `sequence > 1`. Reject as `INVALID_SEQUENCE` or `INVALID_PREVIOUS_HASH` respectively.

**Step 6 — Chain validation.** Compute `object_commitment` from the unsigned payload. If `sequence > 1`, retrieve the accepted object at sequence `N-1` in the same `(issuer, stream_id)` sequence space and compute its `object_commitment`. Verify that the candidate's `previous_hash` equals that commitment. Compute the expected `chain_hash` using the accepted predecessor's chain hash and the candidate's object commitment. Verify that the candidate's `chain_hash` matches. Reject as `CHAIN_MISMATCH` on any failure.

**Step 7 — Signature input construction.** Compute `signature_input` from the unsigned payload and the chain hash.

**Step 8 — Signature verification.** Verify the Ed25519 signature over `signature_input` against the public key authorized for this object type and stream. For dual-signature objects, verify both signatures over the same input. Reject as `INVALID_SIGNATURE` on any failure.

**Step 9 — Authority validation.** Verify that the signing key's role is authorized for the object type. Verify that the signing key is currently authorized for the stream: not revoked, not superseded at the object's sequence position, and covered by the object's delegation chain. Reject as `UNAUTHORIZED_SIGNER` on any failure.

**Step 10 — Semantic validation.** Apply the object's semantic rules (identity document binding, grant scope, lease policy, and so on).

## B.2 Atomicity

Verification must be pure with respect to accepted state. No step in the procedure may advance or mutate accepted stream state. Only after all ten steps pass is the object committed to local state as a single atomic operation.

If processing fails at any step, the verifier retains its previous accepted state. There is no partial application.

## B.3 Rejection classes

| Class | Trigger |
|-------|---------|
| `MALFORMED_ENCODING` | Not valid canonical CBOR |
| `MALFORMED_ENVELOPE` | Envelope field missing, mistyped, or unknown field present |
| `UNKNOWN_SCHEMA` | `domain_separator` not in registry |
| `MALFORMED_SCHEMA` | Schema-specific field fails validation |
| `INVALID_SEQUENCE` | `sequence` is 0 or otherwise invalid |
| `INVALID_PREVIOUS_HASH` | Presence of `previous_hash` does not match `sequence` |
| `CHAIN_MISMATCH` | `previous_hash` or `chain_hash` does not match stream state |
| `INVALID_SIGNATURE` | Signature does not verify |
| `UNAUTHORIZED_SIGNER` | Signing key is not authorized |
| `REVOKED` | Signing key or target object is revoked |
| `EXPIRED` | Validity interval has elapsed |
| `FORK_DETECTED` | Stream is in `FORKED` state |

Individual schemas may define additional rejection classes for schema-specific failures.

# Part C — Security Model in Full

## C.1 Threat enumeration

Each threat below names the attacker's goal, the mechanism they would use, the defense the protocol provides, and the outcome.

**T1 — Identity forgery.** Attacker attempts to claim another principal's Peer ID. Mechanism: signs an identity document with their own key. Defense: identity documents must be signed by the declared identity root. Outcome: signature verification fails; object rejected as `INVALID_SIGNATURE`.

**T2 — Authorization forgery.** Attacker attempts to create a grant authorizing themselves without the issuer's consent. Mechanism: signs a grant with their own key. Defense: grants must be signed by an authorization key that the verifier trusts for that issuer. Outcome: signature verification fails or authority validation fails.

**T3 — Endpoint poisoning.** Attacker with access to a rendezvous server serves a stale or false endpoint. Mechanism: returns a cached or fabricated reachability record. Defense: reachability records are signed by the device key; verifier validates signature and tries candidates in order. Outcome: connection delay; the attacker cannot redirect to a different peer because the endpoint's identity is bound to the device key, not to the address.

**T4 — Relay observation.** Attacker operates a relay and attempts to read forwarded traffic. Mechanism: inspects packets. Defense: transport encryption (WireGuard, QUIC, or TLS). Outcome: relay sees only ciphertext plus timing and volume metadata.

**T5 — Passive network observation.** Attacker intercepts traffic on the network. Mechanism: taps the wire. Defense: transport encryption. Outcome: same as T4.

**T6 — Lost or stolen device.** Attacker gains physical access to a device with active leases. Mechanism: uses the device to access protected services. Defense: revocation (short propagation window) plus lease expiration (bounded exposure). Outcome: access is denied within `min(revocation_propagation, lease_expiry)`, typically 30 minutes to 30 days depending on policy.

**T7 — Sybil attack.** Attacker generates many identities to flood infrastructure. Mechanism: creates random Peer IDs and publishes dummy documents. Defense: the protocol does not prevent identity creation. Mitigation is at the deployment layer: rate limits, admission control, resource quotas. Outcome: attacker can create identities but cannot consume unbounded resources.

**T8 — Authorization escalation.** An authorized subject attempts to perform an operation beyond its grant. Mechanism: requests a capability not covered by the grant. Defense: network-level capability check plus application-level role check. Outcome: rejected at whichever layer first detects the mismatch.

**T9 — Authorization key compromise.** Attacker obtains an Authorization Key's private material. Mechanism: signs grants, leases, or revocations with the compromised key. Defense: `KeyRevocation` with `effective_sequence` bounds the exposure to forward time. Outcome: existing grants and leases survive; objects signed at or after the effective sequence are invalid.

**T10 — Device key compromise.** Attacker obtains a Device Key. Mechanism: signs reachability records. Defense: Device Keys sign only reachability; reachability is untrusted. Outcome: attacker can publish false endpoints, causing connection delays, but cannot affect authorization.

**T11 — Identity Root compromise.** Attacker obtains the Identity Root's private material. Mechanism: forges identity documents, grants, relationships, revocations. Defense: none in-band. Outcome: the entire principal is compromised. Recovery requires out-of-band coordination.

**T12 — Replay.** Attacker captures a valid object and presents it later. Mechanism: re-sends the captured bytes. Defense: validity intervals and sequence requirements. Outcome: expired objects are rejected; sequence-based rollback is rejected.

**T13 — Man-in-the-middle during pairing.** Attacker intercepts the pairing exchange and attempts to impersonate one of the parties. Mechanism: intercepts messages and substitutes their own key. Defense: PAKE with transcript binding and human verification. Outcome: pairing fails unless the attacker knows the shared secret.

**T14 — Clock skew.** Verifier's clock is significantly different from the issuer's. Mechanism: causes absolute-validity checks to misclassify. Defense: relative validity for leases. Outcome: authorization survives up to the lease duration in either direction of skew.

## C.2 Explicit non-properties

The protocol does not provide:

- **Anonymity.** Peer IDs are stable identifiers.
- **Metadata confidentiality against a global observer.** Traffic patterns, timing, and endpoint addresses are visible to infrastructure operators and on-path observers.
- **Protection against OS compromise.** If the device's operating system is compromised, all keys on that device are compromised.
- **Post-quantum security.** Ed25519 is vulnerable to quantum attacks.
- **Availability under adversarial conditions.** A determined attacker can deny access even if it cannot forge authorization.
- **Protection against authorized-but-malicious peers.** A peer with a valid grant can abuse it within the scope of the grant.

## C.3 Blast radius

| Compromised asset | Identity | Authorization | Reachability | Notes |
|-------------------|----------|---------------|--------------|-------|
| Identity Root | total | total | total | Everything under the principal is compromised |
| Authorization Key | no | total (forward) | no | Existing grants/leases survive until expiry |
| Device Key | no | no | total | Only reachability is affected |
| Service Key | no | no | no | Only service metadata is affected |
| Rendezvous server | no | no | partial | Can serve stale endpoints; cannot forge authorization |
| Relay | no | no | no | Metadata only; cannot decrypt |
| Application | no | no | no | Cannot exceed capabilities granted to it |

## C.4 Compromise response procedures

**Authorization Key compromise.** The Identity Root publishes a `KeyRevocation` targeting the compromised key with an `effective_sequence`. All objects signed by the compromised key at or after that sequence become invalid. Existing grants and leases signed before that sequence remain valid. A new Authorization Key is provisioned and legitimate grants are re-issued under it.

**Device Key compromise.** The Identity Root publishes a `KeyRevocation` targeting the device key and removes the corresponding entry from `device_bindings` in the next identity document. The device can no longer sign reachability. Reachability records previously signed by the device are rejected as untrusted.

**Identity Root compromise.** There is no in-band recovery. The principal must establish a new identity through an out-of-band mechanism (social coordination with peers, or an agreed threshold protocol added in a future version). Peers who previously trusted the old root must be informed out of band.

## C.5 Implementation requirements

Implementations must:

- Use constant-time comparisons for cryptographic operations.
- Validate canonical CBOR before semantic processing.
- Use standard library cryptographic implementations; do not implement primitives directly.
- Use OS-provided randomness for key and nonce generation.
- Clear private key material from memory after use.
- Not log private keys, credentials, or lease contents.
- Enforce rate limits on rendezvous queries and relay sessions.
- Validate timestamp ranges and sequence bounds.

Implementations should:

- Use hardware-backed key storage where available.
- Persist accepted stream state durably across restarts.
- Use monotonic time for relative-validity calculations.
- Provide diagnostic logging that does not include secrets.

# Part D — Connectivity and Relay in Full

## D.1 Preference order

When establishing a connection, the verifier attempts the following in order and stops at the first success:

1. **Local LAN** via mDNS or equivalent. Fastest; no cost.
2. **Direct IPv6** if both peers have routable addresses.
3. **Direct IPv4** if both peers have routable addresses.
4. **NAT traversal** via STUN/ICE-style candidate exchange and hole-punching.
5. **Relay** using the highest-priority relay in the reachability record.
6. **Alternative relay** in priority order if the first fails.

The preference order is not a protocol rule; it is the natural outcome of lower-latency and lower-cost paths being tried first. An implementation may deviate if it has information that changes the tradeoffs.

## D.2 Relay capability model

A relay advertises its capabilities as a set of properties:

- Maximum bandwidth
- Maximum concurrent sessions
- Maximum total bytes per session
- Maximum session duration
- Supported transport families (IPv4, IPv6)
- Expected latency characteristics
- Expected availability
- Geographic region
- Operator policy

The protocol does not standardize how these properties are published. The default is that a relay's reachability record includes a set of endpoints, and each endpoint's priority is determined by the reachability publisher's local policy.

## D.3 Raspberry Pi 3B reference numbers

These are illustrative, not normative. Actual numbers depend on the specific operating system, kernel networking stack, WireGuard implementation, and traffic profile.

- **WireGuard-encrypted forwarding throughput:** 100–150 Mbps
- **Concurrent sessions:** 100–200 depending on packet size
- **Per-session state:** roughly 500 KB
- **Base system memory:** roughly 200 MB
- **Power draw:** roughly 5 W sustained
- **Electricity cost at $0.12/kWh:** roughly $0.50/month
- **Hardware cost:** roughly $35 one-time
- **Break-even against electricity alone:** roughly 70 months

The Pi's practical limit is almost never the Pi. It is the residential uplink. A home connection with 20 Mbps upload can relay 20 Mbps regardless of what the Pi is capable of.

## D.4 Residential ISP constraints

Residential internet is asymmetric. Typical values:

- **Download:** 100–500 Mbps
- **Upload:** 5–50 Mbps
- **NAT type distribution:** roughly 5% symmetric, 20–30% address-restricted, 50–60% port-restricted, 5–15% full-cone
- **UPnP availability:** roughly 30–50% of routers
- **Data caps:** often 500 GB–1 TB/month on non-fiber connections

These constraints determine where relays are actually useful. A peer with full-cone NAT may be reachable directly. A peer with symmetric NAT likely requires a relay. A peer on satellite internet may have very high latency regardless of path.

## D.5 Multipath constraint list

These design decisions in V1 exist because they preserve the option to add multipath in a future version without a breaking change:

- Reachability records may carry multiple endpoint candidates.
- Relay tickets specify a source peer and a destination peer, not a specific connection.
- Path identity is distinct from connection identity.
- Authorization is path-agnostic.
- Relay selection is not encoded into any signed object.

No V1 implementation is required to use multiple paths. The constraints simply ensure that a V1.5 or V2 implementation can introduce multipath without changing the object model.

## D.6 Relay operator economics

These are illustrative. Actual margins depend on infrastructure costs, user mix, and pricing.

**Small operator, 10 Gbps capacity:**
- Monthly infrastructure cost: roughly $1000
- Users at $7/month average: 200
- Monthly revenue: $1400
- Monthly margin: $400 before developer share
- Developer share at 20%: $280
- Net margin: $120

**Medium operator, 100 Gbps capacity:**
- Monthly infrastructure cost: roughly $10,000
- Users at $7/month average: 2000
- Monthly revenue: $14,000
- Monthly margin: $4000 before developer share
- Developer share at 20%: $2800
- Net margin: $1200

**Large operator, 1 Tbps capacity:**
- Monthly infrastructure cost: roughly $100,000
- Users at $7/month average: 20,000
- Monthly revenue: $140,000
- Monthly margin: $40,000 before developer share
- Developer share at 20%: $28,000
- Net margin: $12,000

The economics improve with scale and with better peering arrangements. Operators that own their own fiber or have favorable peering have significantly lower per-Gbps costs.

# Extensions

This document describes future extensions to the Grid Network protocol that are not part of the v1 kernel but are architecturally anticipated.

---

## 1. Multi-hop Relay and Onion Anonymity

### 1.1 Multi-hop Relay

Basic multi-hop forwarding is straightforward:

```
A → R1 → R2 → R3 → B
```

Each relay in the path forwards encrypted traffic without terminating the end-to-end encryption. The kernel supports multi-hop relay by chaining RelayTicket objects and RelayNodeRecord advertisements.

### 1.2 Onion Anonymity

Tor-grade anonymity is not simply “three relays.” A genuinely strong anonymity system requires:

- Circuit construction with layered encryption
- Relay compromise resistance
- Guard relay selection
- Timing correlation resistance
- Packet-size correlation resistance
- Traffic volume correlation resistance
- Circuit rotation mechanisms
- Congestion management
- Malicious relay resistance
- Sybil attack resistance
- Relay discovery without metadata leakage
- Exit behavior controls
- Metadata leakage prevention
- Active attack resistance

For example, even if a path `A → R1 → R2 → R3 → B` is encrypted, an observer who can watch both ends might correlate traffic timing and volume.

The kernel can support anonymity without being redesigned around anonymity, but a genuinely strong anonymity system is a major subsystem in its own right.

Another reason to defer it: a genuinely strong anonymity system is a major subsystem in its own right.

### 1.2 Anonymity Extension Architecture

Future anonymity extensions would introduce:

- **OnionRouting** object type for multi-hop circuit construction
- **LayeredEncryption** for per-hop encryption
- **CircuitRotation** mechanism for periodic path rotation
- **GuardRelay** designation for entry guard selection
- **ExitPolicy** for exit relay behavior control
- **TrafficPadding** for volume/timing correlation resistance

These extensions would operate as layers above the kernel, composing the existing RelayNodeRecord and RelayTicket primitives.

---

## 2. Advanced Extensions (Future)

### 2.1 Multi-path Connectivity

Future versions may support concurrent use of multiple paths for increased bandwidth, redundancy, and latency optimization. This requires:

- PathSet abstraction for managing multiple concurrent paths
- Adaptive scheduling algorithms
- Congestion control across paths
- Redundancy/FEC for reliability

### 2.2 Dynamic Relay Markets

Future relay markets could enable:

- Automated credit exchange between operators
- Geographic scarcity pricing
- Quality-of-service guarantees
- Reputation systems

### 2.3 Metadata Protection

Future extensions may provide:

- Rotating pseudonyms for rendezvous lookups
- Traffic padding for volume/timing correlation resistance
- Mix network integration for stronger anonymity

# Known Limitations

This document identifies design limitations that are inherent to the Grid Network protocol's architecture and cannot be fixed by adding mechanisms. Each limitation is named, explained, and accompanied by its mitigation and boundary.

---

## 1. Stale Anchor / Identity State Distribution Gap

### The Limitation

Two peers who have not communicated in an extended period may not be able to verify each other's current identity state.

**The scenario:** Alice and Bob established a relationship six months ago. Since then, Alice has rotated her device keys (or her identity root). Bob has been offline or has not communicated with Alice. Bob's cached copy of Alice's identity document is stale. Bob has no way to obtain Alice's current identity document or the continuity chain from his anchor to her current state without communicating with Alice — which requires reaching her, which requires her current reachability record, which requires knowing her current authorized device keys.

This is a circular dependency:
- To reach Alice → Bob needs Alice's current reachability record
- To verify the record → Bob needs Alice's current authorized device keys
- To get those → Bob needs Alice's current identity document (or continuity chain)
- To get that → Bob needs to communicate with Alice
- To communicate → Bob needs to reach her

### Why No Protocol Mechanism Can Fix This

The protocol assumes identity state propagates through peer-to-peer contact. When two peers are disconnected, there is no communication path. A protocol mechanism cannot create a path where none exists.

Adding a global state distribution layer (DHT, gossip, blockchain) would:
- Change the trust model (introduce new authorities)
- Add enormous complexity
- Not solve the fundamental problem: if a peer is offline, no protocol can reach it

### Mitigation

1. **Rendezvous serves identity state** (adopted in PROTOCOL.md §30.6): Rendezvous servers accept and serve identity documents and `IdentityContinuity` objects. This provides a centralized but untrusted cache of identity state.

2. **Reachability freshness fields** (adopted in PROTOCOL.md §32.2): `published_at` and `identity_sequence` on reachability records allow a verifier to detect stale state and know when to refresh.

3. **Out-of-band contact**: If neither peer has been online and neither has out-of-band contact, the relationship cannot be revived. This is the boundary.

### Boundary

The protocol guarantees that **if a peer can reach the rendezvous, it can obtain current identity state**. It does **not** guarantee that a peer can reach the rendezvous. If both peers are offline, or neither can reach any rendezvous, the relationship is suspended until one party comes online or out-of-band contact is made.

---

## 2. Split-Brain Identity

### The Limitation

If an identity root is compromised and the attacker publishes a competing identity document, the protocol cannot distinguish the legitimate root transition from the attacker's transition without out-of-band information.

**Why no mechanism can fix this:** No cryptographic mechanism can distinguish "legitimate root rotation" from "attacker-driven root transition" based solely on the signed objects. Both are correctly signed by their respective roots.

### Mitigation

- `IdentityContinuity` dual-signature requirement makes orderly transitions verifiable
- Out-of-band recovery for unplanned transitions (PROTOCOL.md §54.10)
- The verifier's accepted state before the fork is preserved (PROTOCOL.md §54.5.7)

### Boundary

The protocol guarantees that **an orderly root transition is verifiable and auditable**. It does **not** guarantee that a disputed transition can be resolved in-band without prior trust anchor.

---

## 3. Metadata Leakage in Discovery

### The Limitation

Rendezvous servers observe which peers are looking for which other peers, and when. This is inherent to any rendezvous-based discovery system.

**Why no mechanism can fix this:** To discover a peer, you must ask a rendezvous server. The server learns the query pattern. Using multiple rendezvous servers distributes but does not eliminate the leakage. Private Information Retrieval (PIR) or DHT-based discovery would add enormous complexity and still leak metadata at some level.

### Mitigation

- Opaque Peer IDs prevent the rendezvous from linking queries to human identities
- Multiple rendezvous providers allow distribution of trust
- Future: DHT-based discovery (§31 V5) if required

### Boundary

The protocol guarantees that **the rendezvous cannot forge identity, authorization, or revocation**. It does **not** guarantee that the rendezvous cannot observe *who is looking for whom*.

---

## 4. No Availability Guarantee

### The Limitation

The protocol does not guarantee that peers can reach each other. It guarantees that **if** a connection is established, **then** it is authenticated and authorized.

**Why no mechanism can fix this:** Availability depends on network conditions (NAT, firewalls, CGNAT, relay capacity, rendezvous uptime, ISP blocking) that are outside the protocol's control. No cryptographic protocol can force the internet to deliver packets.

### Mitigation

- Relay fallback (§33)
- Multiple rendezvous providers (§31 V2+)
- Direct-first connectivity (§53.11: availability-preserving for connectivity)

### Boundary

The protocol guarantees **authorization correctness** (fail-closed). It does **not** guarantee **availability** (fail-open for connectivity).

---

## 5. PAKE Algorithm Unspecified in V1

### The Limitation

The pairing protocol requires an established PAKE (SPAKE2 or CPace) but does not mandate a single algorithm in V1.

**Why this matters:** Interoperability between implementations requires agreement on the exact PAKE, transcript construction, and identity binding.

### Mitigation

- Documented as a schema gap to be filled in OBJECTS.md §6
- PAKE must be specified before wire protocol (Offer 1)

### Boundary

This is a **schema gap** (fixable), not a design limitation. It will be resolved before V1 release.

---

## 6. Relay Key Rotation Requires OperatorManifest Update

### The Limitation

If the Relay Authority Key is rotated, all relay tickets issued under the old key become invalid unless the OperatorManifest is updated.

**Why this matters:** A coordinator who loses the Relay Authority Key cannot issue new tickets until the OperatorManifest is updated with the new key.

### Mitigation

- `current_relay_authority_key` field added to OperatorManifest (PROTOCOL.md §30.3)
- Relay Authority Key rotation is an operator-level operation

### Boundary

This is an operational consideration, not a protocol failure mode. It is documented and the mechanism exists.

## Future Work

### What It Does Well

**Opaque peer IDs rather than self-certifying IDs.** Peer identity is a principal identifier bound to a signing key through an explicit authorization record, not derived from the key itself. This allows key rotation without identity change, and supports delegation without re-deriving IDs.

**Per-principal relationship assertions.** Authorization is expressed as assertions issued by principals about their own state (device posture, key bindings, revocation decisions), not as permissions granted by a central authority. Each relationship carries its own signed state.

**Effective_sequence on revocation.** Revocation carries an explicit sequence number that orders it relative to other state changes, enabling verifiers to reason about temporal precedence without relying on wall-clock time.

**Separation of lease validity from freshness.** A lease (rendezvous ticket, relay capability, key authorization) has a validity window; freshness is a separate property evaluated by the verifier based on observation recency. This avoids conflating expiration with staleness.

**Revocation as state, not just an event.** Revocation is recorded in the identity continuity chain as a signed object with `effective_sequence`, making it queryable and auditable. A revoked key leaves a verifiable trace rather than disappearing.

**Infrastructure never being authoritative.** Rendezvous, relay, and directory services are replaceable infrastructure. They carry signed state; they do not *become* the source of truth. Authority remains with the signing principals.

**Canonical CBOR with domain separation.** All signed objects use a deterministic CBOR profile (RFC 8949 §4.2.3 length-first map ordering, lexicographic set-element ordering, explicit null/absent semantics) with domain-separated tags per object type. This eliminates encoding ambiguity as a source of verification divergence.

## Purpose

This document addresses a question that comes up whenever someone first encounters Grid Network:

> *"Isn't this just [Tailscale / Headscale / BitTorrent / Bitcoin / WireGuard / DNS] with extra steps?"*

The honest answer is: **yes, in part — and that's the point.** Grid Network does not invent new cryptography, new transports, new relays, or new discovery mechanisms from scratch. It takes the ideas and, where it makes sense, the actual infrastructure implementations that have been proven to work, and it composes them into a system that solves a problem none of them solves alone.

This document explains what Grid Network borrows from each of these systems, what it deliberately does differently, and why the composition is what makes the result useful.

---

## Part I — The premise

### 1. Great systems are great


- **DNS** is the most successful naming system in computing history. It runs the internet, it scales to billions of names, and it has been running for forty years. Whatever you think of ICANN, the underlying technology is a triumph.
- **WireGuard** is the best-designed VPN protocol in existence. It's small, fast, auditable, and formally verified. It has replaced decades of accumulated complexity with a few thousand lines of code.
- **BitTorrent** demonstrated that millions of peers could coordinate without a central server, that bandwidth could be shared peer-to-peer, and that a distributed swarm could be more efficient than centralized distribution.
- **Bitcoin** demonstrated that strangers could agree on a shared history without trusting each other, using cryptographic proofs and economic incentives.
- **Tailscale** demonstrated that mesh VPNs could be pleasant to use. It made remote connectivity a consumer-friendly product rather than a sysadmin chore.
- **Headscale** demonstrated that a proprietary coordination service could be reimplemented by the community, and that self-hosting was possible even for systems not designed for it.

Each of these systems succeeded at something. Grid Network takes those successes seriously.

### 2. But each one solves a different problem

The problem Grid Network solves is not any of these. It is:

> *How do two devices establish and maintain an authenticated, authorized relationship that survives changes to their location, their network, their infrastructure provider, and their physical hardware — without any company being the permanent authority?*

DNS doesn't solve this: it maps names to addresses, not identities to authorizations.

WireGuard doesn't solve this: it provides encrypted transport but not identity, authorization, or discovery.

BitTorrent doesn't solve this: it coordinates content distribution, not authenticated connections.

Bitcoin doesn't solve this: it provides a global ledger but at enormous cost, and it doesn't provide a practical identity layer for normal devices.

Tailscale doesn't solve this: it makes mesh VPNs pleasant, but the identity layer is owned by a company and not portable.

Headscale doesn't solve this: it self-hosts Tailscale's coordination, but inherits Tailscale's account-based identity model.

The problem is real, and none of these systems solves it. But each contributes an idea.

---

## Part II — What Grid Network borrows

### 3. From DNS

**Borrowed:** The idea that names can be resolved to current locations without the resolver being the authority.

**Borrowed:** The concept of a resolver that caches answers and serves them within a TTL.

**Borrowed:** The idea of a globally consistent namespace that doesn't require a central registry to be online for lookups to work.

**Done differently:** DNS names are hierarchical and centrally administered. Grid Network identities are flat and controlled by the participant. There is no ICANN equivalent, no root zone, no delegation hierarchy. This is deliberate — the hierarchy is what creates the concentration of power in DNS.

**Done differently:** DNS names point to addresses. Grid Network identities point to reachability records that are signed by the identity itself. This means the "resolver" never has authority over the answer — it can only serve records that are already signed.

**Why this matters:** Grid Network takes DNS's useful property (names resolve to current locations) and removes DNS's problematic property (names are administered by a hierarchy).

### 4. From WireGuard

**Borrowed:** The idea that transport encryption should be small, auditable, and modern.

**Borrowed:** The idea that the transport layer should not carry application-level authorization. WireGuard does one thing — encrypted transport — and does it well.

**Directly used:** Grid Network uses WireGuard as its preferred transport in V1. It doesn't reinvent encrypted transport.

**Done differently:** WireGuard has no notion of identity, authorization, or discovery. Grid Network provides those as a layer above WireGuard. WireGuard handles the tunnel; Grid Network decides *who* should have a tunnel and *why*.

**Why this matters:** Grid Network doesn't try to replace WireGuard. It uses WireGuard as one of several pluggable transports. This is why the protocol is transport-independent.

### 5. From BitTorrent

**Borrowed:** The idea that peers can coordinate without a central server.

**Borrowed:** The idea that a swarm can be more resilient than a centralized system.

**Borrowed:** The idea that a large number of small contributors can outperform a small number of large ones.

**Borrowed:** The tracker concept — a lightweight service that helps peers find each other, but doesn't relay content.

**Done differently:** BitTorrent swarms coordinate around specific content. Grid Network peers coordinate around identity and authorization. The coordination is more general.

**Done differently:** BitTorrent's trackers are optionally centralized. Grid Network's rendezvous is deliberately replaceable and untrusted — any rendezvous can serve any peer's records, because the records are signed.

**Done differently:** BitTorrent has no notion of authorization. Anyone who can reach a torrent can download it. Grid Network has explicit authorization, with grants, leases, and revocations.

**Why this matters:** Grid Network learns from BitTorrent's peer-to-peer resilience, but applies it to authenticated connections rather than content distribution.

### 6. From Bitcoin

**Borrowed:** The idea that strangers can coordinate without a central authority.

**Borrowed:** The idea that cryptographic proofs can replace institutional trust.

**Borrowed:** The idea that economic incentives can shape behavior.

**Borrowed:** The idea that a chain of hashes can provide a tamper-evident history.

**Done differently:** Bitcoin uses a global consensus mechanism (proof of work, then proof of stake) to agree on a single ordered history. Grid Network does not need global consensus, because its problem is local — verifying one device's identity and authorization doesn't require agreement with the entire network.

**Done differently:** Bitcoin is expensive by design — its security model depends on the cost of attacking it. Grid Network is cheap by design — its security model depends on cryptographic signatures, which are cheap to verify.

**Done differently:** Bitcoin has no identity layer in the practical sense. Addresses are pseudonymous. Grid Network has explicit identity, with device keys bound to principals.

**Why this matters:** Grid Network takes Bitcoin's insight (cryptographic proofs replace institutional trust) without taking Bitcoin's cost (global consensus).

### 7. From Tailscale

**Borrowed:** The idea that Grid Network connectivity should be pleasant to use, with a good user experience.

**Borrowed:** The idea that NAT traversal should be automatic.

**Borrowed:** The idea that relay fallback should be seamless.

**Borrowed:** The idea that the control plane and the data plane should be separated.

**Done differently:** Tailscale's coordination server is the source of truth. Grid Network's rendezvous servers are untrusted and replaceable — the source of truth is the signed objects held by participants.

**Done differently:** Tailscale's identity is account-based. Grid Network's identity is cryptographic and portable.

**Done differently:** Tailscale's protocol is proprietary. Grid Network's protocol is open.

**Why this matters:** Grid Network learns from Tailscale's product design while avoiding Tailscale's dependence on a single company.

### 8. From Headscale

**Borrowed:** The idea that a proprietary coordination service can be reimplemented by the community.

**Borrowed:** The idea that self-hosting coordination is possible and valuable.

**Borrowed:** The idea that a well-designed protocol can be reimplemented, even when the original protocol is not designed for it.

**Done differently:** Headscale reimplements Tailscale's protocol. Grid Network designs its protocol to be open from the start, so that reimplementation is a first-class concern rather than a reverse-engineering effort.

**Done differently:** Headscale inherits Tailscale's account-based identity. Grid Network defines its own identity model, designed for portability.

**Why this matters:** Headscale demonstrates that a community can sustain a self-hosted coordination layer. Grid Network is designed to make that easier, not harder.

### 9. From other systems

Grid Network also learns from:

**Matrix:** Federated protocols are hard. Matrix's experience with homeservers and federation shows that you have to think carefully about how coordination works, and that "federation" is often a euphemism for "everyone has to run infrastructure they don't want to run." Grid Network takes the parts of Matrix's design that work (public-key identity, signed events) and avoids the parts that cause friction (mandatory homeservers).

**SSH:** Trust-on-first-use is a valid security model for some contexts, but it's not sufficient for a general identity protocol. Grid Network provides explicit identity binding through pairing, with a clear verification path.

IPFS provides content-addressed storage but is hard to make useful for ordinary users. Grid Network does not address content storage.

**Kerberos:** Short-lived tickets with a central authority are a proven access-control model. Grid Network takes the "short-lived authorization" idea (leases) but removes the central authority (grants are verified locally).

---

## Part III — The composition is the point

### 10. Why composition matters

None of the individual ideas Grid Network borrows is new. DNS, WireGuard, BitTorrent, Bitcoin, Tailscale — each has been done. What Grid Network does is *compose them* into a coherent system that solves a problem none of them solves alone.

The composition has these properties:

1. **Identity is portable.** (Borrowed from DNS's namespace stability, but applied to cryptographic identity.)
2. **Transport is pluggable.** (Borrowed from WireGuard's "do one thing well" philosophy.)
3. **Discovery is untrusted.** (Borrowed from BitTorrent's tracker model, with signatures added.)
4. **Authorization is local.** (Borrowed from Kerberos's ticket model, without the central authority.)
5. **Intermediaries cannot become authorities.** (Borrowed from Bitcoin's insight about cryptographic proofs replacing institutional trust.)
6. **The user experience is polished.** (Borrowed from Tailscale's product design.)

The result is something that doesn't exist yet: an identity and authorization layer that is open, portable, untrusted by default, and usable by ordinary people.

### 11. Learning from successes

Grid Network's design decisions come directly from what these systems got right:

- **From DNS:** A resolver caches answers within a TTL and serves them without the authority being online.
- **From WireGuard:** A small protocol can be more secure than a large one, because it's more auditable.
- **From BitTorrent:** Millions of peers can coordinate without central infrastructure if the coordination is simple enough.
- **From Bitcoin:** Cryptographic signatures can replace institutional trust, but only where you actually need trustless consensus — and often you don't.
- **From Tailscale:** Users will adopt a Grid Network VPN if the experience is pleasant, even if it's technically complex underneath.
- **From Headscale:** A well-designed protocol can be reimplemented by the community, even if the original was proprietary.

### 12. Learning from failures

Grid Network also learns from what these systems got wrong:

- **From DNS:** Centralized administration creates concentration of power. Grid Network avoids it by making identities self-sovereign.
- **From Bitcoin:** Trustless consensus is enormously expensive. Grid Network avoids it by making the trust problem local, not global.
- **From Matrix:** Mandatory homeservers create friction. Grid Network makes rendezvous replaceable and optional.
- **From IPFS:** Decentralization for its own sake is not useful. Grid Network decentralizes only where decentralization solves a specific problem.
- **From early P2P:** "Anyone can participate" often means "spam and abuse dominate." Grid Network makes participation possible without making abuse free, using rate limits, credit systems, and admission control at the edges.

### 13. The composition is more than the sum

Grid Network is not "DNS + WireGuard + BitTorrent" or "Tailscale but decentralized" or "Bitcoin for connectivity."

Those properties are:

- **Portable identity.** No company owns it.
- **Local verification.** Works offline, works under partition.
- **Untrusted infrastructure.** Rendezvous and relays can be malicious.
- **Polished UX.** Ordinary people can use it.
- **Developer integration.** Applications can consume it via API.
- **Sustainable funding.** The commercial layer funds the protocol.

No existing system has all six of these. That's the gap Grid Network fills.

---

## Part IV — The developer angle

### 14. Grid Network is not a competitor to these systems — it's a layer above them

This is the framing that matters most for developers:

> Grid Network is not a replacement for Tailscale, WireGuard, DNS, or BitTorrent. It's a layer above them that solves a problem they don't solve: portable identity and authorization for device connectivity.

A developer who adopts Grid Network is not being asked to give up WireGuard (Grid Network uses it), give up DNS (Grid Network doesn't interfere with it), or give up anything they already have. They're being asked to add a layer that solves the identity-and-authorization problem they've been solving badly on their own.

### 17. Integration options

Different projects have different integration needs:

**Full integration.** The app bundles the grid agent and integrates with its local API. Users pair once, and connectivity just works.

**Optional integration.** The app detects whether a grid agent is installed and uses it if present. If not, the user sees a friendly prompt: "Install Grid Network to enable remote access."

**Recommended integration.** The app's documentation recommends Grid Network, and setup instructions include installing the agent.

**Transparent integration.** The app runs an HTTP proxy that speaks to a local grid agent on behalf of the user. The app doesn't even need to know the agent exists.

Each approach is valid. The simplest for the app is transparent; the most integrated is full. The right choice depends on the app's architecture and the developer's preferences.

---

## Part V — Why this leads to disruption of commercial entities

### 18. The disruption is not the goal

The goal of Grid Network is not to disrupt commercial connectivity vendors. The goal is to make basic trusted connectivity an open capability that anyone can use, the way email is an open capability that anyone can run a server for.

But if the protocol succeeds, disruption is a consequence. Not because Grid Network attacks these vendors, but because it makes the thing they sell — the coordination layer — a commodity that nobody needs to pay for.

### 19. What gets disrupted, and why

The commercial entities that get disrupted are those whose business model depends on being the *coordination authority*.

- **Managed mesh VPNs.** Their value proposition is partly "we make connectivity easy" (which Grid Network also does) and partly "we're the permanent coordinators of your network" (which Grid Network doesn't need). The first part survives; the second part doesn't.

- **Tunnel services.** Their value proposition is "we get you through the firewall." Grid Network still needs relays for the hard cases, but the relay layer is replaceable. What was a sticky platform becomes a competitive market.

- **Cloud identity providers.** Their value proposition is "we know who your users are." Grid Network doesn't replace user identity — that's still the app's job — but it decouples device identity from user identity, which some vendors currently bundle.

- **DDNS services.** Their value proposition is "we track your changing IP." Grid Network's reachability records do this, signed by the device itself. DDNS becomes less necessary.

- **Remote-access products.** Any product whose main value is "you can reach your stuff from anywhere" is competing with Grid Network. Some will adapt by adding value on top (compliance, support, integration). Others will lose their market.

### 20. What survives

The vendors that survive are the ones whose value is not in being the coordination authority:

- **Reliable relays.** Anyone can run a relay, but running a *good* relay — low latency, high bandwidth, geographically distributed, with good support — is still valuable. The market for commercial relays is real, and it's competitive.

- **Enterprise integration.** Enterprises pay for Okta integration, MDM support, compliance documentation, and SLAs. None of that is provided by the protocol; it's provided by vendors. This market is likely to grow.

- **Managed infrastructure.** Some users don't want to run anything themselves. The market for "managed Grid Network infrastructure" is real, and it's competitive.

- **Support.** Users who need help still pay for help. The market for support is real.

- **Hardware appliances.** Preconfigured routers, NAS devices, and home-server appliances that ship with Grid Network built in are a natural product.

- **Developer tooling.** Applications that want to integrate Grid Network need tooling, documentation, and support. This is a market.

The pattern is: **vendors that compete on quality survive; vendors that compete on lock-in do not.** This is the same pattern that happened with email, TLS, and every other commodity infrastructure layer.

### 21. Why this is healthy

The disruption is not a tragedy. It's a shift. Vendors who built their business on owning the customer's identity will find that harder. Vendors who built their business on being genuinely excellent at what they do will find the market *better*, because they're no longer competing with incumbents who win by default.

The user wins because they get portable identity and can switch providers freely. The ecosystem wins because more vendors can compete on quality rather than on access. The protocol wins because it becomes a shared foundation rather than a fragmented set of incompatible products.

---

## Part VI — The polish and simplicity angle

### 22. Simplicity is the point

The reason Grid Network exists is not that it's technically novel. It's that it makes the *use* of identity and connectivity simple for ordinary people.

Today, connectivity is a chore. You have to install Tailscale, make an account, log in with Google, add devices, approve devices, configure ACLs. Or you have to run a VPN, set up certificates, configure NAT traversal, manage a relay. Or you have to open ports and hope.

Grid Network's goal is to make this as simple as scanning a QR code. The user should not have to understand identity, authorization, reachability, relays, or any of the machinery. They should see a working connection and not think about it.

### 23. What polish looks like

- **Pairing:** a QR code, a code, a confirmation. Done in seconds.
- **Discovery:** automatic. No configuration.
- **Connectivity:** automatic. Direct when possible, relayed when necessary.
- **Revocation:** one tap to remove a device.
- **Recovery:** a clear path when something is lost.

None of this requires the user to understand the protocol. It requires the protocol to be well-designed enough that the machinery is invisible.

### 24. Why polish is what makes this disruptive

The reason commercial vendors get disrupted is not that they're bad at their job. It's that their job becomes unnecessary. Grid Network doesn't beat them at their job; it makes the job itself less necessary by removing the friction that justified paying for it.

If connectivity "just works" the way email "just works," then the market for "we make connectivity work" shrinks. What remains is the market for "we make connectivity work *at scale*, with *guarantees*, for *enterprises*." That market is real, and it's competitive. But it's a different market than the one where vendors currently sell "we coordinate your network."

### 25. The economic sense

The phrase "in a way that makes economic sense" is important. Grid Network is not free in the sense that resources are free. Bandwidth costs money. Relays cost money. Developers cost money.

What makes economic sense is:

- **Bandwidth is paid for proportionally.** Free users get free-tier bandwidth. Paid users pay for priority. Contributors earn credits. Enterprises buy reserved capacity.
- **Infrastructure is owned by whoever runs it.** No central operator collects rent on infrastructure that users could run themselves.
- **Developers are funded by the value the network creates.** Commercial operators contribute a share of revenue to protocol maintenance.
- **Portability reduces the cost of switching.** Users aren't locked in, so vendors can't charge rent on the lock-in.

The net effect is that the economic value of connectivity shifts from "owning the coordination layer" to "operating reliable infrastructure." The first is a rent; the second is a service. Grid Network makes the first unviable and the second competitive.

## Part VII — Summary

### 26. The one-sentence summary

> Grid Network stands on the shoulders of DNS, WireGuard, BitTorrent, Bitcoin, Tailscale, and Headscale — borrowing their ideas, their successes, and their lessons, and composing them into a system that solves the problem none of them solves alone: portable, open, authenticated connectivity for ordinary people.

### 27. The one-paragraph summary

Grid Network is not a competitor to the systems it learns from. It uses WireGuard for transport, borrows DNS's resolver model for reachability, learns from BitTorrent's peer coordination, applies Bitcoin's insight about cryptographic trust, adopts Tailscale's product polish, and takes Headscale's lesson about community self-hosting. The result is not "DNS but decentralized" or "Tailscale but open" — it's a new composition that produces properties none of these systems has: portable identity, local verification, untrusted infrastructure, polished UX, developer integration, and sustainable funding. If it succeeds, it won't be because it beat anyone. It will be because it made something previously hard into something that just works.

# Grid Network — Design Rationale

---

## Executive Summary

Grid Network is a **control plane for identity, authorization, and reachability** that sits above whatever networking already exists.

Not a VPN. Not a tunnel. Not a replacement for WireGuard, IPv6, or any transport protocol. A layer that answers questions *about* devices and their permissions, using signed objects that participants hold and verify themselves.

---

## The Problem

Every self-hosted service, personal server, home automation system, and private application eventually hits the same wall:

> *"How do I reach this from somewhere else?"*

This is not a niche problem. It affects home servers running Jellyfin, Immich, Nextcloud; home automation running Home Assistant; NAS devices with file sharing; personal code repositories; backup infrastructure; game servers; development machines you want to SSH into.

The problem is not technical. The technology exists. The problem is **institutional**: no vendor-neutral way exists to establish and maintain portable identity and authorization.

### The Three Bad Choices Today

**Choice 1 — Expose to the Internet:** Open a port, forward on the router, hope nothing scans you. Firmware vulnerabilities, default credentials, automatic scanners, Shodan exposure, ransomware attacks.

**Choice 2 — Use a Proprietary Tunnel/Grid Network VPN:** Tailscale, Cloudflare Tunnel, ZeroTier, ngrok. Beautiful products, excellent UX. But: company owns the device graph, access policies, relationship data. Company is a permanent authority. If company changes terms, gets acquired, shuts down, changes pricing — user adapts or loses network. Underlying protocol is proprietary: no third-party implementations, no competing providers, can't switch without rebuild.

**Choice 3 — Build It Yourself:** Run your own VPN, manage certificates, handle dynamic DNS, deal with CGNAT, NAT traversal, relay infrastructure, revocation, offline state. Works, but requires sysadmin expertise most people don't have. Even technical people spend weekends debugging it.

### The Hidden Cost

The obvious framing: "This is inconvenient." The real framing: **"The ability to reach your own devices has become a subscription."**

A decade ago: open a port (risky but yours) or run a VPN (awkward but yours). Today: the easy path is to sign up for a service. Works beautifully. But you don't own your network anymore. You're renting the ability to reach your own stuff.

This is the same story as email, social media, cloud storage, and every other layer of the internet. Convenience slowly becomes dependence. It's not a conspiracy; it's how products work. But it creates a specific cost: **you don't own your digital relationships.** Your home server's relationship to your phone is mediated by Tailscale's servers. If Tailscale disappears, the relationship disappears. Not because the technology failed. Because you never actually owned it.

---

## The Solution

Grid Network is a **control plane for identity, authorization, and reachability** that sits above whatever networking already exists.

### The Three Questions

1. **Who is this?** — A cryptographic identity, controlled by the participant.
2. **What is it allowed to do?** — A signed authorization, verified locally.
3. **Where can I find it?** — An ephemeral reachability record, refreshed as networks change.

Every question is answered by signed objects. No answer requires contacting a central authority.

### What Grid Network Is Not

- Not a decentralized VPN (VPN is a transport; Grid is a control plane above transports)
- Not a DNS replacement (DNS maps names to addresses; Grid maps identities to reachability with authorization)
- Not an anonymity network (peers are identified; metadata visible to infrastructure operators)
- Not a blockchain (no global consensus, no ledger, no mining, no token)
- Not a peer-to-peer file system (no distributed storage)
- Not a company (no operator, no owner, no central authority)
- Not a Tor/I2P/Freenet replacement (those provide anonymity through routing)

---

## Five Key Design Properties

### Property 1 — Identity is Portable
A device's identity is a cryptographic keypair. It does not depend on any account, server, provider, vendor, or central authority. Survives network changes, device replacement, provider changes, infrastructure changes, service outages.

### Property 2 — Authorization is Local
A device verifies authorization itself, using state it holds locally. Enables offline authorization, partition-tolerant authorization, authority-independent verification, immediate revocation.

### Property 3 — Reachability is Ephemeral
Where a device currently is, is not part of its identity. It's a hint, refreshed as networks change. Enables seamless network transitions, IP address changes, untrusted rendezvous, infrastructure portability.

### Property 4 — Infrastructure is Untrusted
Rendezvous servers, relays, and any infrastructure can be operated by anyone, including parties the user doesn't trust. Enforces: no rendezvous server decides authorization, no relay decrypts content, no infrastructure becomes authority, every intermediary can be replaced.

### Property 5 — Protocol is Open
No proprietary component. Any implementation can speak to any other. Enables community implementations, competitive relays, interoperable infrastructure, no lock-in to any vendor, independent security audits.

---

## The Core Security Invariant

> Given a set of locally trusted anchors, authenticated protocol objects, known revocations, accepted chain state, and recorded observation history, a verifier must be able to deterministically establish the identity, authorization, validity, and freshness state of a peer **as of the verifier's most recent observation**, without contacting an authority.

This means:
- Rendezvous infrastructure CANNOT define identity
- Relays CANNOT define authorization
- DNS CANNOT define identity
- IP addresses CANNOT define identity
- WireGuard keys CANNOT by themselves define app-level authorization
- Temporary pairing codes CANNOT become permanent credentials

## How It Works in Practice

Alice sets up her home server. She installs a Grid agent. Bob wants to access Alice's Jellyfin server remotely. Alice gives Bob a QR code. Bob scans the QR code with his phone. The QR code initiates a pairing:

1. Devices exchange public keys (temporary pairing keys)
2. Bob's phone signs "I recognize Alice's server"
3. Alice's server signs "I recognize Bob's phone"
4. Mutual recognition established

Now Alice can grant Bob access:
1. Alice creates a Grant: "Bob's phone can stream from Jellyfin"
2. Grant is valid for 30 days, covers Jellyfin.stream capability
3. Bob's phone automatically renews the lease monthly

Bob accesses Jellyfin from anywhere:
1. Bob's phone reaches Alice's server (direct if possible, via relay if not)
2. Server verifies: "Bob's phone has a valid grant for Jellyfin.stream"
3. Grant verified locally (no contact with Alice or authority needed)
4. Connection established

Bob loses his phone:
1. Alice revokes the grant
2. The revocation is signed by Alice's identity root
3. Distributed to the network through normal protocol mechanisms
4. Bob's phone can no longer access anything
5. Alice issues a new grant to her new phone

Six months later Bob is offline:
1. Grant remains unchanged (signed, offline-verifiable)
2. Lease expires (short-lived proofs of current validity)
3. Bob comes back online
4. Bob requests fresh lease
5. Alice's system auto-renews (depending on policy)
5. Access restored

Alice switches infrastructure providers:
1. Alice's identity (Peer ID) doesn't change
2. Alice's relationships (with Bob) don't change
3. Alice's grants (to Bob) don't change
4. Only the rendezvous server changes
5. Bob's phone automatically finds Alice's reachability at new server
6. Everything continues working

**Key insight:** The infrastructure is replaceable. The relationships are not.

Every time you want to reach your own devices from outside your home, you have to choose between exposing them to the internet or renting a company's account to coordinate them. Grid Network is a cryptographic protocol that makes the coordination layer portable. Your identity and your relationships belong to you, not to a vendor. The result is private connectivity that behaves like email: anyone can run the infrastructure, anyone can switch providers, and no company gets to decide whether your network exists.

Why Grid Network matters for projects like Immich, Jellyfin, Home Assistant, Nextcloud

The problem every self-hosted app eventually hits

Imagine you're building Immich. You're a photo app. Your job is photos: face recognition, albums, sharing, mobile sync, ML tagging. That's a full-time problem on its own.

Then one day a user says: "I want to access my photos from my phone when I'm not at home."

Now you have to answer a question that has nothing to do with photos:

· How does the phone find the server? The IP changes. The router blocks inbound traffic. The user is on CGNAT.
· How do we authenticate the phone? An account? A device token? A QR code?
· How do we authorize it? Does everyone in the family have the same access? Can a phone upload but not delete?
· What if the user's server goes down for a week? Do we cache the last known location?
· What if the user changes ISPs? Does the pairing survive?
· How do we handle NAT traversal?
· What if the network blocks peer-to-peer? Do we need a relay? Who runs it?
· How do we encrypt the traffic? Do we use a TLS certificate we can't have? Do we build our own?

Every one of these questions is a real, hard problem. Every one of them has a different answer depending on who's asking. And every one of them is completely orthogonal to "how should photos be organized."

This is the moment most self-hosted projects start making bad decisions.

The three bad decisions every project makes

Option 1: Use a central account system. "Just sign up for our cloud, and we'll handle connectivity through our servers." Now you're operating a cloud service. You're responsible for uptime, for user data, for abuse, for GDPR, for support. Congratulations — you've stopped being a photo app and become an infrastructure company. This is what Immich's paid cloud tier does, and it's a real burden that most projects can't afford.

Option 2: Tell users to run Tailscale. "Just install Tailscale and point the app at the local IP." This works, technically. But now every user of your app has to know what Tailscale is, has to make an account with a company, has to install a second piece of software, and has to understand that the app only works if that other thing is running. It's a support burden and an adoption barrier, and it makes your app's documentation depend on a third party you don't control.

Option 3: Roll your own. "We'll build a custom tunnel between the mobile app and the server." This is what a lot of projects attempt, and it's the worst option. You end up reimplementing identity, authorization, discovery, NAT traversal, relays, revocation, and every edge case, badly, with a small team, and you ship security bugs because you're a photo app team, not a networking team.

Every self-hosted app eventually picks one of these three, and all three are bad for different reasons.

What Grid Network changes

Grid Network is a protocol that lets an app say: "I don't need to solve this. Somebody else already did."

Instead of the app building or renting connectivity infrastructure, the app talks to a local Grid Network agent running on the user's device. The agent handles:

· Identity — who is this user, who is this device?
· Pairing — how did this phone first connect to this server?
· Discovery — where is the server right now?
· NAT traversal — how do we get through the router?
· Relay fallback — what if direct connection fails?
· Authorization — is this phone allowed to upload? To delete?
· Revocation — what if the user loses this phone?
· Freshness — is the authorization still current?

The app asks the agent one question: "Give me a connection to Alice's Immich server." The agent answers with a local URL. The app treats that URL like any other local service. It doesn't know or care whether the connection is going over LAN, direct internet, or a relay.

This means the app doesn't have to:

· Know about NAT. The agent handles it.
· Know about relays. The agent handles it.
· Know about certificates. The agent handles mutual authentication.
· Know about pairing. The agent handles the QR code / code exchange.
· Know about revocation. The agent handles it.
· Know about offline state. The agent handles leases.
· Know about key rotation. The agent handles it.

The app just uses a URL. That's it.

Why this matters more than it sounds

The immediate benefit is that apps get a whole category of functionality for free. But there's a larger structural benefit that's worth naming.

Right now, every self-hosted app reinvents the same connectivity layer, badly. Immich has its own sharing. Jellyfin has its own remote access. Home Assistant has its own Nabu Casa cloud. Nextcloud has its own federation. Syncthing has its own relay infrastructure. Paperless, PhotoPrism, Vaultwarden, Gitea, and dozens of others each have a partial answer to "how do I let users reach this remotely."

Every one of these is a different implementation of the same concepts:

· Identity
· Pairing
· Authorization
· Discovery
· NAT traversal
· Relay
· Revocation

And every one of them is a separate attack surface, a separate maintenance burden, a separate documentation problem, and a separate support queue.

Grid Network says: this is a shared problem. It should have one shared answer. The app should consume the shared answer, not reinvent it.

The analogy is to what happened with TLS. Twenty years ago, every app built its own encryption. Some used SSL, some used a custom protocol, some used nothing. Today, every app links against a TLS library and gets the same audited, correct implementation for free. Nobody writes their own crypto anymore, and the whole ecosystem is more secure as a result.

Grid Network wants to do for device identity and connectivity what TLS did for transport security. It's a shared, audited, correct primitive that apps consume instead of reinventing.

The specific advantages for a project like Immich

Concretely, here's what Immich gets from adopting Grid Network instead of building its own:

No cloud dependency. Immich doesn't have to run a service to make remote access work. Users install a Grid Network agent, pair their phone, and the phone reaches the server. Immich never sees a byte of coordination traffic.

No account system. Immich doesn't have to manage user accounts at the network layer. The Grid Network agent handles identity. Immich can still have its own user accounts for the application — Alice vs. Bob vs. Guest — but not for the network. Those are different problems and separating them is a good thing.

No NAT traversal code. This is a huge one. NAT traversal is genuinely hard: STUN, ICE, hole punching, TURN fallback, IPv6 reachability, CGNAT handling, symmetric NAT detection, port prediction. Every app that tries this either does it wrong or invests a huge amount of engineering. Immich gets it for free.

No relay infrastructure. If direct connectivity fails, the Grid Network agent falls back to a relay. Immich doesn't have to run one.

No QR code / pairing protocol. Pairing a phone with a server is a subtle cryptographic problem — you need a PAKE, you need to prevent man-in-the-middle, you need to bind the pairing to the actual identities being paired, you need rate limiting. The Grid Network agent handles this.

No revocation. If Alice loses her phone, she revokes the phone's authorization. Immich doesn't have to implement this.

No key rotation. If the server's identity key is compromised, the user rotates it. Immich doesn't have to implement this.

No offline-state handling. If the phone is offline for a week, the Grid Network agent handles whether the authorization is still valid. Immich just sees "connection available" or "connection refused."

No cross-platform complexity. The Grid Network agent has native support for iOS, Android, Linux, macOS, Windows. Immich's mobile app doesn't have to write connectivity code for each platform.

No security review burden for connectivity. The Grid Network protocol is a single, audited, versioned specification. Immich doesn't have to defend its own connectivity code against review — there isn't any.

No documentation burden. "Install Grid Network agent, scan this QR code, done." That's the entire remote access documentation for Immich.

That's a large amount of work Immich doesn't have to do.

The specific advantages for a project like Jellyfin

Jellyfin has a slightly different problem, and it's worth naming because it clarifies what Grid Network actually provides.

Jellyfin is a media streaming server. Its users want to watch movies and shows from wherever they are: home, work, hotel, parents' house. Jellyfin's security model involves identifying users, granting them access to libraries, and streaming media to them over HTTP.

Right now, Jellyfin's remote access story is: "the user has to set up port forwarding, or use a reverse proxy, or install a VPN." None of these are Jellyfin's job. All of them are user-facing friction.

With Grid Network:

· The user installs a Grid Network agent on the Jellyfin server and on the client.
· The user pairs them.
· The Jellyfin client sees the server as a local service.
· Streaming just works, from anywhere.

But there's a subtlety: Jellyfin's application-level authorization — who can see which libraries, who can admin the server, who can add plugins — remains Jellyfin's problem. Grid Network provides network-level identity and authorization. Jellyfin provides application-level authorization. Both are needed, and they're cleanly separated.

This separation is important because it means:

· Jellyfin doesn't have to give up its user model.
· Jellyfin doesn't have to trust the Grid Network agent's authorization for application decisions.
· Jellyfin can use the Grid Network identity as one input among many.

The Grid Network agent says "this connection is from a device that is cryptographically authenticated as Alice's phone." Jellyfin decides "Alice's phone is allowed to stream from the Kids library but not the Horror library." Two different problems, two different layers, no confusion.

The general pattern

The general pattern is this: every self-hosted app has the same list of hard connectivity problems, and none of them are the app's actual job.

The app should be excellent at its domain: photos, media, notes, files, home automation, whatever. It should not be excellent at NAT traversal, key management, relay infrastructure, or offline authorization. Those are solved problems that belong in a shared layer.

Grid Network is the shared layer.

Once an app integrates with Grid Network, it stops carrying connectivity as a burden. It gets:

· Remote access that works out of the box.
· Pairing UX that users actually understand.
· Revocation that actually works.
· Offline state that behaves correctly.
· Cross-platform support for free.
· A shared security model that someone else audits.

And it gives up nothing. The app retains its own user model, its own authorization decisions, its own data, its own service. Grid Network only handles the parts that aren't the app's responsibility.

Think about what HTTP did for the web. Before HTTP, every application built its own protocol for retrieving documents. After HTTP, applications got a shared, universal protocol, and they focused on what made them different.

Think about what TLS did for encryption. Before TLS, every application built its own crypto. After TLS, applications got a shared, audited primitive, and they focused on what made them different.

Grid Network wants to be that for device identity and connectivity. A single shared primitive that every self-hosted app can consume, so that they can spend their engineering effort on the parts of their app that users actually care about.

If it works, a small open-source project in 2028 should be able to say: "remote access works, we use Grid Network for that" — the same way a small project today says "encryption works, we use TLS for that."

That's the win. Not just for users, who get better remote access from more apps. But for developers, who get to stop solving the same problem over and over.

How commercial projects benefit — the "we offloaded SSO, why not this too" argument

The self-hosted story is where Grid Network starts, but the commercial story is where it gets interesting. Because commercial projects have already shown they're willing to offload a whole category of functionality to a third party — and they did it for exactly the same reasons that make Grid Network useful.

The precedent: how commercial apps offloaded sign-on

If you look at what happened to authentication over the last 15 years, it's a story of progressive delegation.

Phase 1 — roll your own. Every app built its own username/password system. Custom hashing, custom password reset, custom session management, custom password policies, custom everything. This was a support nightmare, a security nightmare, and duplicated across every product in the industry.

Phase 2 — use a framework. Apps started using Django's auth, Rails' Devise, Spring Security, passport.js. This was better — you still had your own user database, but at least the crypto was handled by people who knew what they were doing. But you still owned the account, the passwords, the resets, the policy, the compliance.

Phase 3 — offload to an identity provider. Auth0, Okta, Firebase Auth, Cognito, Clerk, Supabase Auth, AWS IAM. The app no longer stores passwords, doesn't handle resets, doesn't manage MFA, doesn't worry about compliance. The app calls an IdP, gets a token, and treats "who is this user" as a solved problem.

Phase 4 — federate to third parties. "Sign in with Google," "Sign in with GitHub," "Sign in with Apple." Now the app doesn't even manage the identity provider — it delegates to a provider the user probably already has an account with. The app gets a token that says "this is [email protected], verified by Google."

The overall trend is unmistakable: every commercial app has progressively decided that user identity is not their problem. They don't want to store passwords. They don't want to manage MFA. They don't want to handle account recovery. They don't want to be the authority on "who is this person."

They've offloaded it because it's expensive, risky, and completely orthogonal to what makes the app valuable.

The same argument applies to Grid Network

Grid Network says: the same thing should happen for device identity, network authorization, and reachability.

Today, commercial apps handle this themselves. A SaaS file-sharing product builds its own device-approval system. A commercial IoT platform builds its own NAT traversal. A remote-desktop product builds its own relay infrastructure. An on-prem enterprise tool builds its own device trust model.

Every one of them is duplicating the same work, badly, and paying for it in engineering, support, and security.

Grid Network says: this is a shared layer. Offload it.

What commercial projects actually gain

1. They stop being network infrastructure companies

A commercial photo-sharing product has to build or buy:

· Device pairing UX
· Device identity and authentication
· Access control between devices
· NAT traversal
· Relay infrastructure
· Revocation when a device is lost
· Offline-state handling
· Cross-platform support for mobile, desktop, and web

None of this is photography. None of it is a competitive advantage. All of it is a cost center.

When they adopt Grid Network, all of that is handled by the Grid Network agent. The app calls Grid Network.connect() and gets a local URL. It doesn't know or care how the connection was established.

The engineering savings are large and immediate.

2. They gain portability of trust relationships

This is subtle but commercially important.

Right now, if a company wants to let employees access internal resources, they build a device trust model. When an employee leaves, they revoke access. When the company switches VPN vendors, they migrate or rebuild all of it.

With Grid Network, the device identity and relationship are independent of the vendor. If the company switches from one Grid Network provider to another — or from commercial to self-hosted — the relationships carry forward. Employee offboarding still revokes the right things. New employee onboarding still establishes the right things. The underlying trust graph doesn't have to be rebuilt just because the infrastructure vendor changed.

For enterprises, this is a real strategic advantage: they can negotiate vendor contracts without the vendor's lock-in being the basis of the negotiation.

3. They gain a credible story for BYOD, IoT, and edge

Modern enterprises have a device sprawl problem. Employees' phones, contractors' laptops, IoT devices, edge sensors, remote sites, partner networks. Every one of these is a connectivity problem with a device identity problem underneath it.

Today, most enterprises handle this with:

· MDM for managed devices.
· An identity provider for users.
· A VPN for network access.
· Custom integrations for edge cases.

Grid Network gives them a unified model for all of these that's independent of the vendor and works across the entire device population. A contractor's phone can be paired to a specific service and only that service. An edge sensor can be paired to its gateway. An executive's laptop can be paired to the internal wiki. All with the same protocol, all with the same revocation model, all with the same offline semantics.

This is a meaningful improvement over the current patchwork.

4. They gain a shared story with open-source and self-hosted worlds

Commercial SaaS products and self-hosted projects often serve the same customers. Someone uses Nextcloud at home and Dropbox at work. Someone runs Jellyfin at home and uses a commercial streaming product for work-related media.

If both the commercial product and the open-source alternative speak the same Grid Network protocol, the user's device relationships are portable between them. A user's phone can be authorized to their home Immich server and to a commercial photo-sharing product they pay for, without the two systems having to coordinate.

This is directly analogous to what happened with "Sign in with Google." A commercial app got the benefit of every user who already had a Google account, without having to build its own identity system for those users.

Grid Network gives commercial products the benefit of every user who already has a Grid Network identity — from their home server, their NAS, their phone, whatever. The commercial product doesn't have to be the origin of the identity; it just has to accept it.

5. They gain enterprise delegation

This is where it gets commercially interesting for large vendors.

A commercial product that ships Grid Network support can say to its enterprise customers: "Device identity and authorization are handled by the Grid Network protocol. Your existing identity infrastructure — Okta, Entra, your MDM — plugs into this at the policy layer. We don't store your device graph; you do. We don't decide who's authorized; you do."

That's a very strong sales pitch in an enterprise market that has become allergic to vendor lock-in and data residency problems. It's the same reason enterprises demand SAML and SCIM support: they want identity to live in their system, not the vendor's.

Grid Network extends that demand from user identity to device identity, which enterprises have wanted for years and haven't had a portable protocol for.

6. They gain a real answer to "what happens if you go out of business?"

Commercial customers, especially enterprise ones, ask this question seriously. "If your company shuts down, what happens to our data? Our devices? Our relationships?"

For most SaaS products, the honest answer is: "You lose everything. You migrate to a new product and start over."

With Grid Network, the honest answer is: "Your device identities, your relationships, and your authorization grants are held by your devices. If we shut down, you plug into a different Grid Network provider and everything keeps working. You migrate your application data separately, but the trust graph is yours."

This is a genuinely stronger answer, and it's the kind of answer that wins enterprise deals in regulated industries.

The commercial framing

You offloaded user authentication to Auth0, Okta, or Google. Why are you still building device authentication, NAT traversal, and revocation infrastructure yourself?

Grid Network is the same story, applied to a problem you've been stuck with. Your app calls a local Grid Network agent, gets an authorized connection, and never thinks about keys, relays, or pairing again.

Your users get remote access that works out of the box. Your engineering team stops maintaining network plumbing. Your enterprise customers get portability of device trust that they've been asking for.

And when you need to sell to the Fortune 500, you can say: "Your identity infrastructure stays yours. We don't own your device graph. We just make it work."

What a commercial vendor actually has to build

Not much. The commercial vendor has to:

2. Integrate with the Grid Network agent's local API — the Grid Network.connect() call.
3. Optionally, expose Grid Network identity to their own application-level authorization (so that "Alice's phone" from the Grid Network layer can be used in their user model).
4. Optionally, provide a service binding in their identity document, so the Grid Network layer knows how their service is identified.

That's it. A few hundred lines of integration code, and the vendor gets:

· Remote access that works from anywhere.
· Pairing UX they didn't build.
· Revocation they didn't build.
· Offline-state handling they didn't build.
· Cross-platform support they didn't build.

· An enterprise sales narrative about not owning their customers' device graph.

The economics are stark. Building this from scratch costs millions and takes years. Adopting Grid Network costs weeks and delivers the same functionality — better, actually, because it's protocol-level rather than product-level.

1. The immediate engineering savings. "You stop writing NAT traversal code, relay code, pairing code, revocation code. That's a team you don't have to hire."

2. The strategic answer to lock-in anxiety. "Your customers stop worrying about whether you'll exist in five years. Their trust graph is portable. You compete on quality, not on lock-in."

3. The enterprise sales story. "You can tell CISOs: your device identities live with you, not with us. We're a conduit, not a chokepoint."

Those three things, together, are a compelling case for a commercial product to adopt Grid Network as a shared layer — even if they have the resources to build something themselves. Because the build-versus-buy calculation tilts heavily toward "share the protocol and compete on top of it."

The analogy to make explicit

The pattern is exactly what happened with TLS. Twenty years ago, every commercial product built its own crypto. They built their own key exchange, their own cipher suites, their own certificate validation. Every vendor had a security team whose job was to reimplement SSL.

Then the industry converged on TLS. Not because anyone was forced to, but because building it yourself was obviously worse. The vendors that adopted TLS early got to market faster, were more secure, and could compete on application features instead of crypto implementations.

Grid Network is the same argument for device identity and connectivity. A commercial vendor that adopts Grid Network is doing what a commercial vendor in 2005 did when they adopted TLS: taking a shared, audited primitive and moving their engineering effort to the parts of their product that customers actually pay for.

The pitch to commercial projects is: you already offloaded sign-on. Offload this too. It's the same calculation.

# Threat Model

Security properties and non-properties of Grid Network v0.6.2.

---

## 1. Adversary Model

### 1.1 Adversaries We Protect Against

1. **Malicious peers** — Peer tries to impersonate another peer or forge authorizations
2. **Malicious rendezvous** — Rendezvous operator tries to MITM or forge reachability
3. **Malicious relay** — Relay operator tries to decrypt traffic or forge authorizations
4. **Eavesdropper** — Third party tries to intercept traffic or observe grants
5. **Network observer** — ISP or state actor tries to observe metadata
6. **Lost device** — Stolen phone contains valid authorization keys
7. **Insider threat** — Authorized person tries to exceed their authorization
8. **Time-skewed verifier** — Device with incorrect clock verifies leases wrong
9. **Offline attacker** — No internet, but has local access
10. **Replay attacker** — Replays captured packets from old sessions
11. **Sybil attacker** — Creates many fake identities
12. **Denial of service** — Overwhelms infrastructure with requests

### 1.2 What We Do NOT Protect Against

- **Anonymity** — Grid Network is not an anonymity network. Peers are identified. Rendezvous can observe who is talking to whom.
- **Global surveillance** — Network observer can see all reachability hints. Content is protected by transport encryption.
- **Quantum computers** — Ed25519 is vulnerable to quantum attacks. Migration to post-quantum crypto when needed.
- **Root compromise** — If device OS is compromised, all security is lost. Grid Network cannot protect against that.
- **Timezone bugs** — Verifier with wrong clock may incorrectly verify time-based proofs. Out-of-band clock sync is operator's responsibility.

---

## 2. Blast Radius

| Component Compromised | Identity | Relationship | Authorization | Reachability |
|----------------------|----------|--------------|---------------|--------------|
| Peer's Identity Root | TOTAL | TOTAL | TOTAL | TOTAL |
| Peer's Auth Key | No | No | TOTAL | No |
| Peer's Device Key | No | No | No | Reachability only |
| Rendezvous Server | No | No | No | Yes (stale hints) |
| Relay | No | No | No | Metadata only |
| Eavesdropper | No | No | No | No (content encrypted) |

**Key insight:** Separation of key roles limits blast radius.

---

## 3. Failure Semantics (F1–F6 Taxonomy)

### F1: Authorization Failure → Deny
Missing grant, expired lease, revocation applied → Connection denied. System is fail-closed. Missing information never grants access.

### F2: Reachability Failure → Try Alternatives
Rendezvous unreachable, endpoint stale, direct connection fails → Try relay. System is availability-preserving. One infrastructure failure doesn't break existing relationships.

### F3: Clock Skew → Relative Validity Survives
Verifier's clock 1 hour behind issuer's → Relative lease still works. Absolute timestamps would fail. Grid Network uses relative by default.

### F4: Communication Interruption → Cache and Continue
Verifier offline, receives revocation later → Revocation cached, applied when object arrives. No silent state change.

### F5: Fork Detection → Require Resolution
Stream has two objects at same sequence → Fork detected. Requires explicit StreamResolution object. No silent choice.

### F6: Key Compromise → Effective_Sequence Limits Damage
Key compromised, retroactive revocation issued → Objects before effective_sequence remain valid. Damage is limited to forward time.

---

## 4. Security Principles

1. **No authority creates identity** — Identity is self-attested. Peer publishes identity document signed by their own Identity Root. Rendezvous is not authority.
2. **All authorization is local** — Verifier evaluates grants/leases using locally held state. No "call home" required. Offline operation works.
3. **Revocation is terminal** — Once revoked, object cannot become valid again. Prevents subtle bugs from temporary revocation semantics.
4. **Reachability is untrusted** — Reachability records are hints, not ground truth. Any can be stale or malicious. Verifier tries multiple endpoints.
5. **Infrastructure is replaceable** — Every infrastructure component (rendezvous, relay) can be swapped. Peer ID, relationships, and authorizations survive the change.
6. **Layering is strict** — Network authorization (Grid Network) and application authorization (app) are separate. Neither can violate the other.

---

## 5. Compromise Response Procedures

### If Authorization Key is Compromised:
1. Principal publishes key revocation in identity stream
2. Specifies effective_sequence (marks which objects are affected)
3. All future objects signed by that key are invalid
4. Existing leases remain valid until expiry
5. New Authorization Key provisioned
6. New leases issued by new key
**Time to recovery:** Minutes (revocation must propagate via rendezvous)

### If Device Key is Compromised:
1. Principal publishes key revocation
2. Device is now untrusted (can't sign reachability)
3. Remove device from device_bindings in identity document
4. Device is offline
5. User physically removes old device from network
**Time to recovery:** Hours (device physically removed)

### If Identity Root is Compromised:
**NO IN-BAND RECOVERY** (v0.6.2 limitation)

Out-of-band options:
1. Principal contacts other peers who know them
2. Provides proof of ownership (social recovery)
3. Other peers issue new relationship assertions
4. Principal re-establishes network relationships

This is a fundamental limitation of v0.6.2. V2 may add threshold recovery.

---

## 6. Implementation Requirements

### Implementations MUST:
- Use constant-time comparisons for cryptographic checks (prevent timing attacks)
- Validate all CBOR canonicalization before processing
- Implement signature verification with standard libraries (don't roll own crypto)
- Use OS-provided random number generation (don't seed with user input)
- Clear sensitive data from memory after use
- Not log private keys or authorization grants
- Implement rate limiting on rendezvous queries (prevent DoS)
- Validate all timestamps are within reasonable bounds (prevent wrapping)

### Implementations SHOULD:
- Use hardware-backed keys when available
- Support key sharding/threshold (future)
- Implement cache coherence for revocations
- Provide audit logs for sensitive operations
- Support multiple encryption transports (WireGuard, QUIC, TLS)

---

## 7. Attack Scenarios and Mitigations

### Scenario 1: MITM on Pairing
- Attacker intercepts QR code
- Attacker follows pairing flow, claims to be Bob
- **Mitigation:** PAKE requires shared secret (QR code). Attacker doesn't have it.
- **Result:** Pairing fails, attacker cannot impersonate Bob

### Scenario 2: Replay Attack
- Attacker captures grant message
- Attacker replays it months later
- **Mitigation:** Grant has timestamp, lease has expiry. Replayed old lease is invalid.
- **Result:** Attacker cannot gain access with old lease

### Scenario 3: Sybil Attack
- Attacker creates 1000 fake peer IDs
- Attacker floods network with garbage
- **Mitigation:** Grid Network does not prevent Sybil. But relays enforce rate limits. Rendezvous enforces query limits. Cost scales with attack size.
- **Result:** Attacker can create fake peers but cannot flood infrastructure without paying for resources

### Scenario 4: Relay Intercepts Traffic
- Attacker runs a relay
- Attacker tries to decrypt forwarded traffic
- **Mitigation:** Content is encrypted by transport layer (WireGuard). Relay only sees ciphertext.
- **Result:** Attacker sees packet size and count, not content

### Scenario 5: Rendezvous Gives False Reachability
- Attacker runs a rendezvous
- Attacker claims peer is at 192.0.2.1
- **Mitigation:** Verifier treats reachability as untrusted. Tries endpoint. If connection fails, tries others.
- **Result:** Attacker can delay connections but cannot MITM (no key)

### Scenario 6: Grant Forgery
- Attacker tries to forge grant
- **Mitigation:** Grant is signed by issuer's Authorization Key. Attacker doesn't have the key.
- **Result:** Forged grant fails signature verification

---

## 8. Metadata and Privacy Properties

Grid Network provides strong confidentiality and authorization properties but does not provide anonymity of participation.

The following metadata may remain observable depending on transport and deployment:

**Stable identity:** Peer identifiers are intentionally stable and may be correlatable across contexts.

**Rendezvous queries:** A rendezvous operator may observe which participants query for which peers or services and when.

**Relay traffic:** A relay may observe participating network endpoints, session timing, session duration, traffic volume, packet-level metadata available to the transport. It does not necessarily learn protected application content.

**On-path observers:** Network observers may identify peers through transport-level information unless an additional privacy mechanism is used.

These properties are intentional consequences of stable identity and ordinary networking.

**The protocol claims:** Confidentiality of protected content and cryptographic authorization, not anonymity of participation.

Future multi-hop or onion-routed transports may provide stronger privacy without changing the underlying identity or authorization model.

---

## 9. Local Verifier Security State

A verifier's local state is a security-critical asset. It may include:
- Trusted anchors
- Accepted stream state (sequence, chain hash)
- Accepted objects
- Revocation state
- Freshness state
- Monotonic observation history

This state MUST be:
- Durable across normal restarts
- Atomically updated
- Attributable to signed protocol objects
- Protected from unauthorized modification
- Recoverable through safe procedures

The verifier MUST NOT reconstruct trusted state merely from arbitrary received objects after local security state has been lost.

---

## 10. Local State Loss

Local security-state loss is a security-relevant event, not merely an availability event.

If a verifier loses the state necessary to establish that a previously trusted stream is the accepted continuation of its history, the safe behavior is to return to an unknown/untrusted state for the affected authority.

The verifier MUST NOT silently reconstruct authority from untrusted observations.

Recovery should therefore result in one of:
- Restoration of trusted local state
- Explicit re-pairing
- Explicit re-establishment of trust
- Another protocol-defined trusted recovery mechanism

Failure to recover state MUST NOT grant or extend authority.

---

## 11. Failure Semantics (Foundational Invariant)

The following invariant is foundational:

**Failure MUST NOT grant, extend, or change identity or authorization.**

Examples:
- Rendezvous failure does not alter identity
- Relay failure does not alter authorization
- Network failure does not extend a lease
- Clock failure does not create authority
- Reconciliation failure does not create capabilities
- Identity forks do not automatically create authority
- Missing revocation information does not automatically prove that an authorization remains valid
- Local state loss does not justify reconstruction from arbitrary observations

Where current authority cannot be established, the safe result is denial or unknown state.

---

## 12. Endpoint and Key Compromise

The protocol cannot prevent compromise of a machine holding private keys.

If an attacker obtains an Identity Root key, the attacker may obtain the authority represented by that key until the key is revoked or otherwise superseded.

If a Device Key is compromised, the attacker may impersonate the affected device within that key's authority.

If an Authorization Key is compromised, the attacker may exercise that authorization authority within its defined scope.

Therefore implementations SHOULD:
- Minimize key scope
- Separate keys by authority
- Protect private keys at rest
- Support appropriate revocation
- Avoid unnecessary exposure of Identity Root keys
- Use hardware-backed or offline protection where appropriate for high-value deployments

---

## 13. Application and Agent Security

Applications should interact with Grid Network connectivity through the local agent/API rather than receiving unnecessary cryptographic authority.

Preferred model:
```
Application
     │
     │ request authorized connection
     ▼
Grid Network Agent
     │
     │ performs policy and connection work
     ▼
Grid Network transport
```

Applications SHOULD receive the minimum capability necessary to perform their requested operation.

The agent SHOULD NOT expose:
- Unnecessary private keys
- Unrestricted authorization capabilities
- Arbitrary relay credentials
- Unrestricted ability to create identities or grants

The application-facing abstraction is therefore both an API simplification and a security boundary.

---

## 14. Parser and Implementation Security

Protocol implementations MUST treat untrusted encoded objects as hostile input.

Security testing SHOULD include:
- Malformed CBOR
- Duplicate keys
- Noncanonical encoding
- Unsupported types
- Invalid UTF-8
- Invalid normalization
- Oversized arrays/maps
- Excessive nesting
- Oversized integers
- Truncated objects
- Invalid signatures
- Invalid chain hashes
- Invalid predecessor references
- Sequence rollback
- Fork conditions
- Expired objects
- Revoked objects
- Concurrent updates
- Crash/restart during state commit

Implementations SHOULD impose bounded resource usage before performing expensive processing. An object should not be able to cause unbounded memory allocation merely by declaring a large payload.

---

## 15. Anti-Amplification

Public protocol services should avoid turning small unauthenticated requests into disproportionately large responses.

Implementations SHOULD bound:
- Response size
- Lookup results
- Object retrieval
- Pagination
- Unauthenticated work
- Reflection behavior

This reduces the possibility that Grid Network infrastructure can be abused as a traffic amplifier.

---

## 16. Operational Security Boundary

Protocol security does not imply deployment security.

The protocol does not attempt to solve:
- Compromise of the host operating system
- Theft of private keys from compromised hosts
- Insecure key storage
- Malicious software installed on a legitimate device
- Compromised agent binaries
- Malicious package repositories
- Compromised build infrastructure
- Software supply-chain attacks
- Compromised update mechanisms
- Social engineering of recovery procedures
- Insecure administrative practices

These are deployment and operational security concerns.

Implementations and distributions SHOULD address them through appropriate measures such as:
- Signed releases
- Reproducible or independently verifiable builds
- Package provenance
- Secure update mechanisms
- Protected key storage
- Encrypted storage
- Hardware-backed keys where appropriate
- Carefully designed recovery procedures
- Administrative separation

These mechanisms should not redefine the protocol's identity or authority model.

---

## 17. Recovery

Recovery is intentionally separate from the core V1 identity model.

Implementations MUST NOT silently weaken cryptographic authority to make recovery convenient.

In particular, a recovery procedure MUST NOT effectively become:
"Contact the service operator and ask them to reset the identity."

unless that operator is explicitly part of the deployment's chosen trust model.

Recovery mechanisms should be treated as additional authority systems and evaluated separately.

---

## 18. Consensus and Bitcoin-Inspired Principles

The protocol may borrow useful principles from systems such as Bitcoin without adopting blockchain architecture.

Useful principles include:
- Independently verifiable state
- Cryptographic commitments
- Explicit deterministic rules
- Resistance to unilateral database rewriting
- Treating scarce resources as scarce
- Assuming adversarial participants
- Making certain classes of abuse economically costly where appropriate

The protocol does not require:
- A global blockchain
- Mining
- Global proof-of-work
- Global transaction ordering
- A global consensus protocol
- Tokens
- A global ledger

The Grid Network problem is primarily one of local cryptographic trust and authorization, not global agreement over a single universal history.

---

## 19. Threat Categories and Expected Outcome

| Threat Category | Expected Outcome |
|-----------------|------------------|
| Forgery | Cryptographic rejection |
| Replay | Expiration, sequence, freshness, or revocation rejection |
| Stream tampering | Predecessor/chain validation failure |
| Malicious rendezvous | Discovery failure or metadata exposure, not unauthorized access |
| Malicious relay | Availability degradation or metadata exposure, not unauthorized access or plaintext disclosure |
| Sybil identities | Little direct effect unless a higher-level system incorrectly treats identity quantity as authority |
| Resource exhaustion | Bounded by rate limits, quotas, expiration, admission controls, and deployment-level infrastructure protections |
| Endpoint compromise | Outside the cryptographic protocol's protection boundary |
| Local state loss | Unknown/untrusted state until trusted state is restored or trust is re-established |
| Implementation defect | Addressed through conformance tests, fuzzing, differential testing, crash/restart testing, and security review |

---

## 20. Security Review Rule

Before introducing a security mechanism, reviewers SHOULD be able to state all three:

1. What authority or resource does it protect?
2. What specific attack does it prevent or mitigate?
3. What is the failure mode if the mechanism is absent?

If any of these cannot be clearly identified, the mechanism should be considered premature.

This rule exists to prevent security-feature accumulation without a defined security boundary.

---

## 21. Recommended Security Test Program

Implementation should progress through increasingly realistic security tests.

**Cryptographic tests:**
- Canonical encoding vectors
- Signature vectors
- Commitment vectors
- Chain vectors
- Object-ID vectors
- Dual-signature vectors
- Invalid signature tests

**State-machine tests:**
- Sequence advancement
- Rollback
- Forks
- Termination
- Revocation
- Key rotation
- Identity continuity
- Local state loss
- Crash during commit

**Adversarial parsing:**
- Malformed CBOR
- Duplicate fields
- Oversized fields
- Invalid types
- Truncation
- Deeply nested data

**Authorization tests:**
- Missing grant
- Expired grant
- Missing lease
- Expired lease
- Revoked grant
- Stale freshness
- Wrong relationship
- Wrong device
- Wrong service
- Wrong stream

**Infrastructure tests:**
- Malicious rendezvous
- Stale rendezvous
- Malicious relay
- Relay disappearance
- Direct-path failure
- Relay fallback
- Replayed reachability
- Coordinator flooding
- Relay resource exhaustion

**Persistence tests:**
- Restart
- Power loss
- Interrupted commit
- Corrupted local state
- Restored backup
- Missing state
- Recovery

The first normative cryptographic test vector should remain the simple sequence-1 single-signature object already planned for the v0.6.2 implementation process.

---

## 22. Security Roadmap

The following items should be treated as implementation and review priorities rather than automatic additions to the protocol kernel:

1. Canonical encoding verification
2. Signature and commitment verification
3. Stream-state integrity
4. Atomic state transitions
5. Identity/key hierarchy
6. Relationship verification
7. Authorization evaluation
8. Freshness and revocation
9. Identity continuity
10. Direct transport security
11. Relay/rendezvous authority separation
12. Bounded resource consumption
13. Object and message size limits
14. Session and connection limits
15. Expiration and garbage collection
16. Anti-amplification controls
17. Optional computational admission mechanisms where justified
18. Key-compromise handling
19. Metadata/privacy analysis
20. Parser fuzzing
21. Concurrency and race testing
22. Crash/restart testing
23. Persistent-state security testing
24. Normative security test vectors
25. Normative requirements for local security-state durability and safe recovery
26. Explicit operational-security boundary and deployment guidance

---

## 23. Security Design Principle

The protocol should remain intentionally small.

Security mechanisms should be added when they protect a concrete:
- Authority boundary
- Resource
- Trust relationship
- State transition
- Confidentiality property
- Integrity property
- Availability boundary

The project should avoid adding mechanisms merely because an attack is theoretically conceivable.

The preferred question is not:

"Can we add another security mechanism?"

It is:

"What specific boundary are we protecting, what attack crosses that boundary, and what happens if the protection is absent?"

---

## 24. Final Security Position

Grid Network's security does not depend on any single component being universally trustworthy.

Instead:
- Identity establishes who controls a cryptographic authority
- Authorization establishes what that authority may do
- Local state establishes what the verifier currently accepts
- Freshness establishes whether that authority remains current
- Transport establishes how authorized parties communicate
- Rendezvous and relay infrastructure remain replaceable and untrusted

This produces a system in which compromise of an intermediary should normally affect availability or metadata, rather than automatically becoming a compromise of identity or authorization.

The principal security objective is therefore not to make every component trustworthy.

It is to make trust unnecessary outside the boundaries where it is explicitly established.

That is the security property that should be preserved as the implementation evolves beyond v0.6.2.

# Grid Network

This specification was developed with AI assistance.

Grid Network is a cryptographic identity, authorization, and reachability protocol for portable, vendor-neutral device connectivity.

Every self-hosted application eventually needs remote access. Today that access either depends on a vendor (commercial mesh VPNs), requires an expert (self-hosted VPNs), or exposes the user to risk (port forwarding). The structural reason is that coordination has always required somebody to be the authority. Authorities cost money to operate, so somebody has to pay.

Grid Network presents a design that solves coordination without introducing an authority. Identity is a keypair, not an account. Authorization is local, not remote. Discovery is signed, not centralized. Infrastructure is replaceable, not mandatory.

The result is a protocol that costs nothing to operate, requires nobody's permission, and cannot be captured by any single entity. It is designed to be for private connectivity what Linux is for operating systems and TLS is for transport security.

---

## The Problem

Every self-hosted service, every personal server, every home automation system, every private application eventually hits the same wall:

> "How do I reach this from somewhere else?"

This forces every project into one of three bad choices:

1. **Expose to the internet** — Open a port, hope nothing scans you. Firmware vulnerabilities, default credentials, Shodan exposure.
2. **Use a proprietary tunnel/mesh VPN** — Tailscale, Cloudflare Tunnel, ZeroTier, ngrok. The company owns your device graph, access policies, identity. If the vendor disappears, your network loses its definition of who is allowed to talk to whom.
3. **Build it yourself** — Run your own VPN, manage certificates, deal with dynamic DNS, CGNAT, NAT traversal, relay infrastructure, revocation, offline state. Works, but requires sysadmin expertise most people don't have.

---

## The Solution

Grid Network is a **control plane** that sits above existing transports (WireGuard, QUIC, TCP) and answers three questions:

| Question | Answer |
|----------|--------|
| **Who is this?** | Persistent cryptographic identity — opaque Peer ID bound to Identity Root keypair |
| **What is it allowed to do?** | Signed Grants + short-lived Leases with relative validity |
| **Where can I find it?** | Ephemeral signed Reachability Records |

---

## Key Properties

- **Identity is portable** — Survives device replacement, network changes, provider changes
- **Authorization is local** — Offline verification, no central authority required
- **Reachability is ephemeral** — Hints, not ground truth; refreshed as networks change
- **Infrastructure is untrusted** — Rendezvous/relay operators cannot forge auth or identity
- **Protocol is open** — No proprietary components; any implementation can interoperate

# Versioning Policy

Grid Network follows semantic versioning for the protocol specification:

## Format: vMAJOR.MINOR.PATCH

- **v0.6.2** (current, design-review)
- **v0.7.0** (next: test vectors, cleanup)
- **v1.0.0** (stable, long-term support)

## Version Semantics

### PATCH (v0.6.2 → v0.6.3)
- Bug fixes only
- No new features
- No new object types
- No new fields in existing objects
- Backward compatible
- Change process: Maintainer review only

### MINOR (v0.6.2 → v0.7.0)
- New features allowed
- New object types allowed
- New optional fields in objects
- Backward compatible (old objects understood by new implementations)
- Change process: RFC + 14-day discussion + maintainer decision

### MAJOR (v0.6.2 → v1.0.0)
- Breaking changes allowed
- Incompatible changes
- Removal of deprecated features
- Backward compatible: NO
- Change process: RFC + 30-day discussion + consensus required

## Document Versioning

Each document has its own independent version:
- spec/PROTOCOL.md v0.6.2
- spec/OBJECTS.md v0.2
- design/RATIONALE.md v2.0
- commercial/MODEL.md v6.0
- design/LINEAGE.md v1.0

When PROTOCOL.md increments MINOR, dependent docs increment MINOR.
When PROTOCOL.md increments MAJOR, all docs increment MAJOR.

## Support Timeline

- v0.x: Maintained until v1.0.0 ships + 5 years
- v1.x: Maintained for 5 years minimum
- End of support ≠ protocol stops working (implementations can run indefinitely)

# Grid Network — Connectivity Architecture

---

## §1: DIRECT-FIRST PREFERENCE ORDER

When connecting to a peer, the verifier tries these approaches in order:

1. **Local network (mDNS)** — Broadcast mDNS query for peer. If found: try direct connection on LAN. Latency: <10ms typical.
2. **Direct connection (public IP)** — Obtain peer's public IP from reachability record. Try direct P2P connection. Latency: 50-500ms depending on geography.
3. **NAT traversal (STUN/ICE)** — Peer is behind NAT, has no public IP. Use STUN to detect NAT characteristics. Attempt hole-punching. Latency: 200-1000ms. Success rate: 70-85% depending on NAT type.
4. **Relay (fallback)** — Direct connection failed. Use a relay to forward traffic. Latency: 100-500ms. Cost: Consumes relay bandwidth/credits.
5. **Alternative relay** — Primary relay failed or overloaded. Try secondary relay.

**Design principle:** Always try cheaper/faster options first.

---

## §2: RELAY CAPABILITY MODEL

A relay is NOT a proxy. It is a pair-bound packet forwarder.

### What a relay does:

```
Device A (203.0.113.1:51820)
    │
    │ Encrypted packet
    │ From Device A to Device B
    ▼
Relay Server
    │ Sees: packet_size, timestamp, device_a_id, device_b_id
    │ Does NOT see: packet content (encrypted)
    │ Does NOT see: which application
    │
    ▼ Forwards packet
Device B (192.0.2.50:51820)
```

Relay bandwidth is metered by relay ticket (bytes/duration).

### Relay priority classes:

- **Free ticket:** Best-effort bandwidth
- **Standard ticket:** 10 Mbps minimum
- **Priority ticket:** 50 Mbps minimum
- **Dedicated ticket:** Reserved capacity

### Relay CANNOT:
- Decrypt content
- Modify packets
- Forge signatures
- Impersonate either party
- Create new relationships
- Issue grants

### Relay CAN:
- See packet counts
- Observe traffic patterns
- Enforce byte limits
- Apply priority queuing

---

## §3: PATH ABSTRACTION

A "path" is a route from source to destination.

```
Path 1: Direct
  Source → [Internet] → Destination
  Cost: $0, Latency: low

Path 2: Relay A
  Source → Relay A → Destination
  Cost: $0.001/GB, Latency: medium

Path 3: Relay B
  Source → Relay B → Destination
  Cost: $0.001/GB, Latency: medium

Path 4: Relay A → Relay B (future multipath)
  Source → Relay A → Relay B → Destination
  Cost: $0.002/GB, Latency: high
```

Verifier maintains path state: reachability hints, success rates, latencies.

---

## §4: PATH DIVERSITY

**Why multiple relays?** Single relay is single point of failure.

**Solution:** Use multiple relays simultaneously (future multipath).

**Constraints:**
- Do not require multipath for v0.6.2 (too complex)
- Do allow multiple relays in reachability record
- Verifier is free to use any relay or combination

**Economic incentive:**
- Home relays (Raspberry Pi) provide diverse, abundant capacity
- Commercial relays provide reliable, high-capacity backbone
- Together: resilient, distributed infrastructure

---

## §5: RELAY LOAD DISTRIBUTION

Commercial relay operators provision N Gbps of capacity.

```
Total: 100 Gbps

Free users: 20 Gbps (first-come-first-served)
Standard users: 40 Gbps (reserved)
Priority users: 30 Gbps (reserved)
Dedicated: 10 Gbps (reserved per customer)

Idle capacity from Standard/Priority/Dedicated users flows to Free pool.

Result: Free users get opportunistic access to 60 Gbps when Standard/Priority don't use it fully.
```

This model:
- Ensures free users always have capacity
- Rewards paid users with guaranteed bandwidth
- Doesn't penalize paid users for overbooking
- Encourages overprovisioning (more capacity = more free benefit)

---

## §6: GEOGRAPHIC DIVERSITY

**Why geography matters:** Latency depends on geography.

```
Same city: 5-20ms
Same region: 20-100ms
Continent: 100-300ms
Intercontinental: 200-500ms
```

Scarce regions (rural, less-developed) have fewer relays.

**Solution:** Geographic credit multiplier.

```
Relay in NYC (abundant): 1 credit per GB
Relay in rural Nebraska: 2 credits per GB
```

**Not in v0.6.2.** Planned for v1.5 or v2.0.

- Redundancy (one relay down, others work)
- Load balancing (spread traffic across relays)
- Congestion avoidance (pick path with lowest latency)
- Resilience (tolerate packet loss)

### Design considerations:
- PathSet abstraction (collection of paths)
- Preference ordering (direct > relay A > relay B)
- Cost model (cost of using multiple paths)
- Ordering semantics (which packets arrive first?)
- Retransmission (retransmit on all paths or just fastest?)

## §10: NON-PRECLUSION CONSTRAINTS

**Design rule:** No relay architecture decision should preclude future multipath.

**Constraints:**
- Every relay ticket must specify throughput (max bytes/duration)
- Every relay ticket must be pair-bound (source/dest specific)
- Every relay must accept admission control (reject if overloaded)
- Reachability records must support multiple endpoints
- Verifier must be free to choose which relay to use

These constraints allow:
- Single relay today (simple)
- Multiple relays tomorrow (complex)
- Multipath protocols to be added without breaking v0.6.2

# Relays

Relay model, capability advertisement, deployment, and economics for Grid Network.

---

## 1. Relay Model

A relay is infrastructure for forwarding traffic when a direct path is unavailable or undesirable. It is not an identity authority, authorization authority, or ownership authority.

### 1.1 Core Properties

- **End-to-end encryption:** Relays forward ciphertext only. They cannot decrypt application payloads.
- **No authorization authority:** Relays enforce ticket validity, expiration, byte limits, bandwidth limits, session lifetime, and connection limits. They MUST NOT create identities, grant capabilities, establish relationships, or modify authorization.
- **Replaceable:** Any relay can be swapped without changing identity, authorization, or relationships.
- **Untrusted by design:** A malicious relay can drop traffic, delay traffic, refuse service, observe metadata, and consume its own resources. It cannot impersonate services, grant authorization, read content, change identity, create relationships, forge leases, or become an authority.

### 1.2 Connectivity Preference Order

1. **Local LAN** — Direct. No relay.
2. **Direct IPv6** — Direct. No relay.
3. **Direct IPv4** — Direct. No relay.
4. **NAT traversal** — Direct once established. No relay.
5. **Relay** — Direct failed. Fallback.

In mature deployments with widespread IPv6 and working NAT traversal, most traffic never reaches step 5.

---

## 2. Capability Advertisement

Relays advertise capabilities rather than hardware identity.

### 2.1 Advertised Properties

- Maximum concurrent sessions
- Aggregate bandwidth
- Maximum per-session bandwidth
- Maximum bytes per session
- Maximum aggregate or periodic transfer
- Maximum connection lifetime
- Supported transports
- IPv4/IPv6 availability
- Current or estimated utilization
- Geographic/region metadata
- Latency characteristics
- Availability characteristics
- Supported relay modes
- Privacy-related capabilities
- Operator access policy

### 2.2 Capability Profiles

| Profile | Description |
|---------|-------------|
| BASIC | Ordinary encrypted forwarding with resource limits |
| HIGH_CAPACITY | Optimized for high aggregate bandwidth and large concurrent sessions |
| LOW_LATENCY | Optimized for path latency rather than maximum throughput |
| LONG_LIVED | Supports long-duration forwarding sessions |
| COMMUNITY | Operator-volunteered with explicitly declared access/resource policies |
| PRIVACY | Supports additional privacy-oriented forwarding capabilities |

Profiles are descriptive capability groupings, not separate protocol architectures.


### 2.3 Relay Capability Advertisement (Future Extension)

The relay capability advertisement mechanism allows relays to publish their current operational capabilities and capacity for client path selection.

### RelayNodeRecord

A RelayNodeRecord is a signed object published by a relay node to advertise its capabilities and current operational state.

Fields:
- `relay_node_id` — unique identifier for the relay node
- `operator_id` — identity of the relay operator
- `endpoint` — network endpoint (address, port, transport)
- `capabilities` — set of capability profile identifiers (BASIC, HIGH_CAPACITY, LOW_LATENCY, LONG_LIVED, COMMUNITY, PRIVACY)
- `capacity` — current capacity declaration:
  - `max_concurrent_sessions` — maximum concurrent sessions
  - `aggregate_bandwidth_bps` — aggregate bandwidth in bits per second
  - `max_per_session_bandwidth_bps` — maximum per-session bandwidth
  - `max_bytes_per_session` — maximum bytes per session
  - `max_session_duration_seconds` — maximum session duration
- `availability` — availability declaration:
  - `hours_per_day` — hours per day the relay is available
  - `days_per_week` — days per week the relay is available
  - `uptime_percentage` — expected uptime percentage
- `supported_transports` — set of supported transport protocols (WireGuard, QUIC, TCP, etc.)
- `privacy_capabilities` — privacy-oriented capabilities (e.g., onion forwarding, multi-hop support)
- `operator_policy` — operator access and contribution policy:
  - `access` — public, relationship-required, or operator-approved
  - `contribution` — free, paid, or reciprocal
  - `price` — pricing information if applicable
- `geographic_metadata` — geographic and network metadata:
  - `region` — geographic region
  - `country` — country code
  - `network_asn` — autonomous system number
  - `latitude` — optional latitude
  - `longitude` — optional longitude
- `issued_at` — timestamp of record creation
- `expires_at` — optional expiration timestamp

RelayNodeRecord is signed by the Relay Node Key and published to rendezvous servers. Clients use this information for path selection without centralized load balancers.

## 3. Operational State

Static capacity is insufficient. Relays expose current operational state:

```json
{
  "load": {
    "active_sessions": 97,
    "utilization": 0.97,
    "available_bandwidth_bps": 3000000
  }
}
```

Clients use this for path selection without centralized load balancers.

## 4. Path Requirements

Applications express connectivity requirements rather than selecting specific relays:

```json
{
  "direct": "preferred",
  "relay": "permitted",
  "min_bandwidth_bps": 20000000,
  "max_latency_ms": 100,
  "max_hops": 3,
  "ipv6": "preferred",
  "privacy_level": 0,
  "minimum_path_lifetime": "2h"
}
```

The local agent evaluates available paths and selects one satisfying the requirements.

## 5. Low-Power Node Deployment

### 5.1 Raspberry Pi Class Hardware

A relay does not need to terminate encryption. The workload is packet forwarding with validation/association of relay sessions, limit enforcement, and transient state maintenance — not heavy cryptography per packet.

A Raspberry Pi 3B can contribute meaningfully:
- Network interface speed and packets/second are the limiting factors
- 10-50 Mbps forwarding is achievable
- Even small contributions are valuable when thousands of nodes participate

### 5.2 Resource Contribution Granularity

Community nodes don't need enormous bandwidth:
- 5-50 Mbps
- Occasional availability
- IPv6 connectivity
- Geographically useful location
- Particular ISP/ASN

A node useless as a high-performance server can still be valuable as one more independent path.

### 5.3 Path Diversity Value

Many small nodes create path diversity. When direct flow performs poorly, the network can discover alternative paths through multiple relays and distribute traffic dynamically based on throughput, latency, loss, jitter, congestion, and stability.

This addresses the residential internet problem where single flows achieve only a fraction of advertised bandwidth while aggregate multipath throughput can be much higher.

---

## 6. Relay Untrusted Property

This is the strongest architectural property. A malicious relay can:
- Drop traffic
- Delay traffic
- Refuse service
- Observe metadata
- Consume its own resources

But it cannot:
- Impersonate the service
- Grant authorization
- Read end-to-end protected content
- Change identity
- Create relationships
- Forge leases
- Become an authority

**Permissionless infrastructure, permissioned services.**

---

## 7. Storage Principles

Forwarding traffic, connection statistics, and transient reachability observations MUST NOT require persistent storage writes.

Persistent storage is for:
- Identity keys
- Configuration
- Accepted protocol state
- Bounded authorization/revocation information
- Signed objects
- Checkpoints
- Limited logs

This makes inexpensive flash/SD storage viable for relay operators.

---

## 8. Network Self-Healing

Because relays are interchangeable resources, the network doesn't need a single official relay. If Relay A is overloaded, the network chooses Relay B. If Relay B disappears, connections migrate or establish another path.

Optimize around scarce resources rather than pretending scarce resources don't exist.

---

## 9. Direct Connectivity First

The preferred progression is:
1. IPv6 direct
2. Direct IPv4 / NAT traversal
3. Other suitable direct transport
4. Relay
5. Multiple relays / multipath

The application shouldn't care. It asks "Connect me to Service X." The agent figures out how.

# Grid Network — Relay & Rendezvous Operations

---

## Core Architecture: Direct-First Preference Order

When connecting to a peer, the verifier tries these approaches in order:

1. **Local network (mDNS)** — Broadcast mDNS query for peer. If found: try direct connection on LAN. Latency: <10ms typical.
2. **Direct connection (public IP)** — Obtain peer's public IP from reachability record. Try direct P2P connection. Latency: 50-500ms depending on geography.
3. **NAT traversal (STUN/ICE)** — Peer is behind NAT, has no public IP. Use STUN to detect NAT characteristics. Attempt hole-punching. Latency: 200-1000ms. Success rate: 70-85% depending on NAT type.
4. **Relay (fallback)** — Direct connection failed. Use a relay to forward traffic. Latency: 100-500ms. Cost: Consumes relay bandwidth/credits.
5. **Alternative relay** — Primary relay failed or overloaded. Try secondary relay.

**Design principle:** Always try cheaper/faster options first.

---

## Relay Capability Model

A relay is NOT a proxy. It is a pair-bound packet forwarder.

### What a relay does:

```
Device A (203.0.113.1:51820)
    │
    │ Encrypted packet
    │ From Device A to Device B
    ▼
Relay Server
    │ Sees: packet_size, timestamp, device_a_id, device_b_id
    │ Does NOT see: packet content (encrypted)
    │ Does NOT see: which application
    │
    ▼ Forwards packet
Device B (192.0.2.50:51820)
```

Relay bandwidth is metered by relay ticket (bytes/duration).

### Relay priority classes (from commercial model):

- **Free ticket:** Best-effort bandwidth
- **Standard ticket:** 10 Mbps minimum
- **Priority ticket:** 50 Mbps minimum
- **Dedicated ticket:** Reserved capacity

### Relay CANNOT:
- Decrypt content
- Modify packets
- Forge signatures
- Impersonate either party
- Create new relationships
- Issue grants

### Relay CAN:
- See packet counts
- Observe traffic patterns
- Enforce byte limits
- Apply priority queuing

---

## Path Abstraction & Diversity

A "path" is a route from source to destination. Verifier maintains path state: reachability hints, success rates, latencies.

### Why multiple relays?
Single relay = single point of failure. If relay goes offline/overloaded/censors, peer becomes unreachable.

### Diversity types:

**Geographic diversity** — Relays in different regions (NYC, Virginia, NJ) provide redundant paths.

**Provider diversity** — Home Pi relay + AWS + Linode + DigitalOcean. If AWS fails, others continue.

**Autonomous System (AS) diversity** — Relays in different BGP ASes (Cogent, Telia, Level3, Global Crossing). Failure at any one AS → other paths continue.

**Network redundancy** — Primary: direct; Secondary: relay 1; Tertiary: relay 2 (different ISP); Quaternary: relay 3 (different country).

Verifier tries all automatically. User never explicitly chooses.

## Relay Load Distribution (Commercial)

Commercial relay operators provision N Gbps capacity.

```
Total: 100 Gbps

Free users: 20 Gbps (first-come-first-served)
Standard users: 40 Gbps (reserved)
Priority users: 30 Gbps (reserved)
Dedicated: 10 Gbps (reserved per customer)

Idle capacity from Standard/Priority/Dedicated users flows to Free pool.

Result: Free users get opportunistic access to 60 Gbps when Standard/Priority don't use it fully.
```

This model:
- Ensures free users always have capacity
- Rewards paid users with guaranteed bandwidth
- Doesn't penalize paid users for overbooking
- Encourages overprovisioning (more capacity = more free benefit)

# Grid Network

This specification was developed with AI assistance.

Grid Network is a cryptographic identity, authorization, and reachability protocol for portable, vendor-neutral device connectivity.

Every self-hosted application eventually needs remote access. Today that access either depends on a vendor (commercial mesh VPNs), requires an expert (self-hosted VPNs), or exposes the user to risk (port forwarding). The structural reason is that coordination has always required somebody to be the authority. Authorities cost money to operate, so somebody has to pay.

Grid Network presents a design that solves coordination without introducing an authority. Identity is a keypair, not an account. Authorization is local, not remote. Discovery is signed, not centralized. Infrastructure is replaceable, not mandatory.

The result is a protocol that costs nothing to operate, requires nobody's permission, and cannot be captured by any single entity. It is designed to be for private connectivity what Linux is for operating systems and TLS is for transport security.

---

## The Problem

Every self-hosted service, every personal server, every home automation system, every private application eventually hits the same wall:

> "How do I reach this from somewhere else?"

This forces every project into one of three bad choices:

1. **Expose to the internet** — Open a port, hope nothing scans you. Firmware vulnerabilities, default credentials, Shodan exposure.
2. **Use a proprietary tunnel/mesh VPN** — Tailscale, Cloudflare Tunnel, ZeroTier, ngrok. The company owns your device graph, access policies, identity. If the vendor disappears, your network loses its definition of who is allowed to talk to whom.
3. **Build it yourself** — Run your own VPN, manage certificates, deal with dynamic DNS, CGNAT, NAT traversal, relay infrastructure, revocation, offline state. Works, but requires sysadmin expertise most people don't have.

---

## The Solution

Grid Network is a **control plane** that sits above existing transports (WireGuard, QUIC, TCP) and answers three questions:

| Question | Answer |
|----------|--------|
| **Who is this?** | Persistent cryptographic identity — opaque Peer ID bound to Identity Root keypair |
| **What is it allowed to do?** | Signed Grants + short-lived Leases with relative validity |
| **Where can I find it?** | Ephemeral signed Reachability Records |

---

## Key Properties

- **Identity is portable** — Survives device replacement, network changes, provider changes
- **Authorization is local** — Offline verification, no central authority required
- **Reachability is ephemeral** — Hints, not ground truth; refreshed as networks change
- **Infrastructure is untrusted** — Rendezvous/relay operators cannot forge auth or identity
- **Protocol is open** — No proprietary components; any implementation can interoperate

Object encoding defines how identity streams, grants, revocations, pairing records, and reachability records serialize to CBOR, sign with Ed25519, and reference each other.

## §2 Canonical CBOR Profile

Canonical encoding per RFC 8949 §4.2.3 (canonical form): definite-length arrays/maps/strings/bytes; no duplicate map keys; floats as smallest representation; no tags unless required; byte strings in lexicographic order where order matters; integers in smallest representation.

> **PENDING DECISION:** D-01 (stream identity model affects envelope / stream encoding rules); D-02 (chain base affects sequence encoding at §3.5). See [`../../design/decisions/DR-0001-stream-identity.md`](../../design/decisions/DR-0001-stream-identity.md), [`DR-0002`](../../design/decisions/DR-0002-chain-base.md).

## §3 Object Serialization / §3.5 Chain Base Encoding

Objects serialize as CBOR map with required fields: `domain_separator` (§58), `sequence`, `previous_hash` (or base for init), content fields, `signature`. Sequence increments by 1 per identity stream (§11). Chain base (§3.5): `previous_hash` for sequence=0 derived per D-02.

> **PENDING DECISION:** D-02 (chain base derivation — affects §3.5 init); D-04 (revocation pinning — affects sequence rules / previous_hash content). See [`DR-0002`](../../design/decisions/DR-0002-chain-base.md), [`DR-0004`](../../design/decisions/DR-0004-revocation-pinning.md).

## §4 Common Stream Envelope

Envelope = `domain_separator` (string) + `sequence` (uint) + `previous_hash` (bytes, 32B) + `document_payload` (map/array) + `signature` (bytes, Ed25519 64B). Domain separators fixed per §58 (e.g., `"grid-v1-identity"`, `"grid-v1-authorization"`, `"grid-v1-revocation"`). Signature covers `domain_separator || sequence || previous_hash || payload_canonical`.

> **PENDING DECISION:** D-01 (stream model affects envelope assignment — single vs split); D-13 (Ed25519 strict encoding of payload and domain separator). See [`DR-0001`](../../design/decisions/DR-0001-stream-identity.md), [`DR-0013`](../../design/decisions/DR-0013-ed25519-and-references.md).

## §5 Signature Semantics and Verification

Ed25519 (RFC 8032). Public key = 32 bytes; signature = 64 bytes. Verification: decode canonical CBOR payload; construct signed message = `domain_separator || sequence || previous_hash || canonical_payload` (exact concatenation, no length-prefix on domain); verify with Ed25519 `verify()` strict (no lenient encoding — D-13). Failure = reject (v0.6.2; four-output proposal NOT here — see §9 / DR-0003).

> **PENDING DECISION:** D-13 (Ed25519 strictness — encoding rules, domain separator format, length handling). See [`DR-0013`](../../design/decisions/DR-0013-ed25519-and-references.md).

## §1 Abstract / §2 Core Security Invariant / §3 Design Goals / §4 Non-Goals

**Abstract.** Grid Network is an identity-, authorization-, and reachability-centric peer protocol using cryptographic identity roots, sequence-ordered identity histories, relationship-scoped assertions, signed grants/leases/capabilities, key revocation with pinning (pending D-04), pairing via PAKE (D-06), and rendezvous/reachability/relay layers. It requires no central authority; authorization is local; identity is a keypair.

**§2 Core Security Invariant.** A peer accepts an authorization statement only when: (a) the identity stream from root through sequence verifies against the root public key with strict Ed25519 (§58, D-13); (b) the authorization record is signed by an authorized key role (§9); (c) no revocation of the signing key or authorization exists at or before the record's sequence (§18–§20, D-04); (d) the peer's local verification state (§47) accepts the stream; and (e) freshness (§40, D-08) and clock/reboot (§40, D-12) conditions are met.

> **PENDING DECISION:** D-01 (stream identity model), D-02 (chain base derivation), D-03 (verifier outcomes/classification — four-outcome proposal NOT promoted; §14 stays v0.6.2 with PENDING D-03), D-04 (revocation pinning / fields), D-13 (Ed25519 strictness / domain separators). See [`../../design/decisions/DR-0001-stream-identity.md`](../../design/decisions/DR-0001-stream-identity.md), [`DR-0002`](../../design/decisions/DR-0002-chain-base.md), [`DR-0003`](../../design/decisions/DR-0003-verifier-outcomes.md), [`DR-0004`](../../design/decisions/DR-0004-revocation-pinning.md), [`DR-0013`](../../design/decisions/DR-0013-ed25519-and-references.md).

**§3 Design Goals.** (1) No central authority — identity = keypair; (2) Local authorization — grants/leases evaluated at peer; (3) Stream-verifiable history — each identity history ordered, pinned, verifiable; (4) Revocation with pinning — revoked keys cannot be replayed; (5) Pairing via PAKE — human-coordinated; (6) Reachability without exposure — rendezvous, relay, reachability records; (7) Offline operation — peers verify from local stream state.

**§4 Non-Goals.** (1) Global naming / DNS replacement (though rendezvous may use domain labels); (2) Application-layer protocol definition (application integration deferred, §55); (3) Multi-device synchronization (V1.1 / extension); (4) Commercial relay economics (extension, D-24); (5) Licensing commitment (D-25 deferred); (6) Implementation-language mandate (D-26 non-normative).

**§48 Security State Machines.** States: UNVERIFIED → VERIFYING → ACCEPTED / REJECTED; transitions on stream update, revocation, clock change, root rotation. Failure = REJECTED (safe denial); not ACCEPTED by default.

**§49 Authority Domains.** Authorization bounded by root / key-role scope; a grant from root A does not apply to identity root B; cross-root references only via explicit delegation (not V1).

**§50 Threat Model / §51 Compromise Model** (preserved from v0.6.2 — entries include: malicious rendezvous (§33); malicious relay (§33); root compromise (§22); key compromise (§21); replay (§18, D-04); inference (§7, D-07); DoS (§11 resource limits, D-11); man-in-the-middle pairing (§24–§29, D-06)).

> **PENDING DECISION:** D-04 (replay prevented by pinning); D-07 (inference prevented by stream privacy); D-11 (DoS bounded by limits); D-06 (MITM prevented by PAKE).

**§52 Service Identity / §53 Failure Semantics / §54 Reconciliation / §55 Application Integration**

**§52 Service Identity.** Service = peer + service record (§10); service auth via Service Key (§9, D-09/V1.1) or root; service identity does not create new authority.

**§53 Failure Semantics.** Failure = authorization denied (safe); failure does not grant access; failure events logged locally; no remote failure notification required (privacy, §7).

**§54 Reconciliation.** Peers reconcile streams (§11) by comparing highest sequence + previous_hash; conflicts resolved by sequence + root signature; checkpoints (§19, D-19) speed reconciliation.

> **PENDING DECISION:** D-19 (checkpoint format); D-01 (stream split affects reconciliation); D-20 (multi-store replication conflicts).

**§55 Application Integration.** Protocol defines authorization / reachability; application defines resource / action; integration via capability (§15) and local authorization (§16–§17). Deferred to v1.1 / extension; needs application-specific profile (not normative here).

> **Status:** NEEDS AUTHOR INPUT — §55 application-integration profile requires design of capability-to-application-resource mapping (not in v0.6.2 source). Preserve until application-layer profile completed.

**§56 V1 Scope / §57 Deferred Features / §58 Signing-Authority Matrix / §59 Implementation Requirements / §60 Test Vectors / §61 Conformance Scenarios / §62 Future Extensions / §63 Project Structure / §64 Versioning / §65 Triage**

**§56 V1 Scope.** Identity + authorization + reachability + pairing + rendezvous + revocation + stream verification; excludes: multi-device sync, application-layer relay economics (D-24), licensing (D-25), non-HTTPS transport (D-21), multi-store replication (D-20), recovery key (removed). See [`../../design/decisions/DR-0022-v1-minimal-profile.md`](../../design/decisions/DR-0022-v1-minimal-profile.md).

> **PENDING DECISION:** D-22 (profile definition); D-01–D-13 (blocking V1); D-23 (vectors).

**§57 Deferred Features.** Recovery Key (removed from V1); relay operator economics (EXT); multi-store (EXT); non-HTTPS transport (EXT); application integration profile (v1.1); licensing (D-25); language mandate (D-26 non-normative).

**§58 Signing-Authority Matrix.** Root signs identity docs + history + grants + revocations + rotation; Relationship Key (if D-09) signs assertions/terminations; Service Key signs service records; Authorization Key (delegated) signs grants; each with domain separator (§58). Signature = Ed25519 (strict, D-13); domain = context string (e.g., "grid-v1-identity").

> **PENDING DECISION:** D-13 (Ed25519 strict encoding / domain separators); D-09 (key roles / delegation); D-04 (revocation signature fields).

**§59 Implementation Requirements.** Must implement §58 (strict Ed25519), §11 (stream verification), §18–§20 (revocation), §24–§29 (pairing contract, D-06), §30–§31 (rendezvous V1). Vectors (§60) required for conformance (§61). CI gates: CDDL validation, vector diff, cross-reference checker, fuzz smoke (see `CONTRIBUTING.md`).

> **PENDING DECISION:** D-23 (test vectors / conformance); D-06 (PAKE interop); D-13 (encoding interop).

**§60 Test Vectors / §61 Conformance Scenarios / §62 Future Extensions / §63 Project Structure / §64 Versioning / §65 Triage**

**§60 Test Vectors.** Canonical CBOR + hex outputs for: identity document (§10), stream segment (§11), revocation (§20, D-04 fields), pairing record (§29), authorization (§13), reachability (§32). Generated from reference implementation; regenerated on spec change; diff checked in CI.

**§61 Conformance Scenarios.** Scenarios cover: identity creation (§8); stream verification (§11); revocation (§20); pairing (§24); authorization (§16); reachability (§32); failure (§53); reconciliation (§54). Each scenario = input + expected verification outcome (accept/reject per v0.6.2; four-output proposal only in DR-0003).

**§62 Future Extensions.** Multi-store (D-20), relay economics (D-24), non-HTTPS transport (D-21), application profile (§55), recovery mechanism (out-of-band, not V1), licensing resolution (D-25).

# Versioning Policy

Grid Network follows semantic versioning for the protocol specification:

## Format: vMAJOR.MINOR.PATCH

- **v0.6.2** (current, design-review)
- **v0.7.0** (next: test vectors, cleanup)
- **v1.0.0** (stable, long-term support)

## Version Semantics

### PATCH (v0.6.2 → v0.6.3)
- Bug fixes only
- No new features
- No new object types
- No new fields in existing objects
- Backward compatible
- Change process: Maintainer review only

### MINOR (v0.6.2 → v0.7.0)
- New features allowed
- New object types allowed
- New optional fields in objects
- Backward compatible (old objects understood by new implementations)
- Change process: RFC + 14-day discussion + maintainer decision

### MAJOR (v0.6.2 → v1.0.0)
- Breaking changes allowed
- Incompatible changes
- Removal of deprecated features
- Backward compatible: NO
- Change process: RFC + 30-day discussion + consensus required

## Document Versioning

Each document has its own independent version:
- spec/PROTOCOL.md v0.6.2
- spec/OBJECTS.md v0.2
- design/RATIONALE.md v2.0
- commercial/MODEL.md v6.0
- design/LINEAGE.md v1.0

When PROTOCOL.md increments MINOR, dependent docs increment MINOR.
When PROTOCOL.md increments MAJOR, all docs increment MAJOR.

## Support Timeline

- v0.x: Maintained until v1.0.0 ships + 5 years
- v1.x: Maintained for 5 years minimum
- End of support ≠ protocol stops working (implementations can run indefinitely)
