D-23: TEST VECTORS AND CONFORMANCE PROGRAM
[BLOCKING, HIGHEST IMPLEMENTATION BURDEN]

Problem:
Without byte-exact, machine-verifiable test vectors, two implementations
cannot prove they interoperate. §19 lists desired test categories; D-23 is
the decision on scope, format, and governance.

Option A: Comprehensive vector suite [PROPOSED]

  Vector categories:
    Encoding: valid and invalid CBOR (malformed, non-canonical, oversized).
    Crypto: valid and invalid signatures; Ed25519 edge cases; key revocation.
    Chain: valid and invalid chain sequences; gaps; forks.
    Verifier: one positive and one negative vector per outcome (ACCEPT,
    REJECT(class), DEFER, FORK_EVIDENCE).
    State: relationship state machines; grant/lease transitions; revocation
    effects.
    Pairing: successful and failed PAKE exchanges (per D-06).
    Reboot: clock scenarios (forward, backward, persisted state present/absent).
    Order independence: same object set in different arrival orders; final
    state must be identical.
    Relay/rendezvous: if relay is in V1 (D-24), wire protocol scenarios.

  Format: canonical CBOR + expected outcomes, encoded in a single
  machine-readable file (JSON or YAML metadata, CBOR objects as hex).

  Governance: vectors are generated by the reference verifier (code is
  source; vectors are derived). When spec and vectors disagree, the spec is
  updated, then vectors are regenerated. CI gates on vector equivalence.

  Pros:
    - Definitive: vectors settle disagreements.
    - Testable: every implementation is measured against the same suite.
    - Future-proof: when the spec is updated, vectors change; divergence is
      caught.

  Cons:
    - Large effort: hundreds of vectors, each with setup/assertion/outcome.
    - Maintenance: vectors must be regenerated after any spec change.
    - Tool dependency: reference implementation must be stable before vectors
      can be published.

Option B: Minimal vectors; defer the rest

  Only the critical blockers (CBOR malformation, Ed25519 strictness,
  order-independence property test) are vectorized. Other scenarios are
  tested ad-hoc.

  Pros:
    - Faster: fewer vectors to produce.

  Cons:
    - Interoperability risk: two implementations might both pass critical
      vectors but diverge on scenarios.
    - Not reproducible: ad-hoc tests are not machine-verifiable.

Recommendation:
Accept Option A (comprehensive suite). This is the single highest-value
activity after decisions are closed. Allocate 4–6 weeks after v0.7.0
(decisions) to produce reference implementation, vectors, and a reference
verifier. No v0.8.0 tag without at least 300 vectors and agreement from a
second verifier.

Consequences:
  - New repository: reference/, with a reference verifier and vector generator.
  - New repository: spec/TEST-VECTORS/, with machine-readable vector suites.
  - Conformance tests: every implementation's CI must verify against the
    vector suite; publish results as a conformance matrix.
  - Process: PR to spec/PROTOCOL.md or OBJECTS.md requires corresponding
    vector changes in the same PR (CI gates on no-divergence).
  - Labeling: vectors are "normative" (interoperability depends on them);
    they are part of the specification, not just examples.
