# 1. One-paragraph summary

This session stress-tested the Grid Network design against long-timescale and long-distance scenarios. It surfaced a foundational gap — **the protocol has no state distribution layer** — and produced two design changes that close the most important class of failures: rendezvous servers will serve identity state in addition to reachability, and reachability records will carry a state-freshness field. It also produced a second round of failure scenarios that are mostly documentation additions or operator-policy concerns rather than protocol changes. The session confirms the priority order for future work: complete the object model first, then wire protocols, then NAT traversal, then credit settlement, then prior-art expansion.

---

# 2. What was decided

Two design changes were adopted. Both need to be incorporated into the archive.

## 2.1 Rendezvous serves identity state

**Change:** Rendezvous servers will accept and serve identity documents and `IdentityContinuity` objects, in addition to reachability records.

**Rationale:** The protocol assumes identity state propagates through peer-to-peer contact, but this fails when peers are disconnected — which is exactly when synchronization matters most. Without this change, a peer who hasn't communicated with another peer in months cannot verify that peer's current state, because the peer's anchor may be stale and there is no way to obtain current state.

**What this affects:**

- Rendezvous layer's scope, not the object model. The endpoints for publication and query are extended; the objects themselves are unchanged.
- Rendezvous remains untrusted. Identity documents are still signed by their issuers; the rendezvous cannot forge them.
- Peers still need to be able to *reach* the rendezvous. If they can't, this change doesn't help. That's still a limitation, but it's a narrower one.

**Where this goes in the archive:**

- Part 7 (protocol), §30 (Rendezvous): add a subsection on scope.
- Part 2 (document inventory): note that rendezvous now serves three object types (reachability, identity documents, continuity).

**Wire-level implications:** Two new endpoints when the wire protocol is specified (Offer 1):

- `POST /v1/identity` — publish an identity document (and optionally the continuity chain to the publisher's previous anchor)
- `GET /v1/identity/{peer_id}` — fetch the current identity document for a peer

## 2.2 Freshness fields on reachability records

**Change:** `ReachabilityRecord` gains two required fields: `published_at` (wall-clock time) and `identity_sequence` (the sequence number of the publisher's latest accepted identity document).

**Rationale:** A verifier that fetches a reachability record has no way to know whether its cached copy of the publisher's identity document is current. With `identity_sequence`, the verifier can compare: if the verifier's cached identity state is at a lower sequence than the record claims, the verifier knows to refresh before using the record.

**These are additions to the initial schema, not a version bump.** V1 hasn't shipped, so the `ReachabilityRecord` schema is still being completed. These fields go into it as required fields.

**Where this goes in the archive:**

- Part 8 (OBJECTS.md §6), `ReachabilityRecord` schema: add the two fields.
- Part 7 (protocol), §32 (Reachability): describe the verifier's use of `identity_sequence`.
- Part 9 (security model): note that stale state is detectable via this field.

# 3. What was found

## 3.1 First failure-mode round (Scenarios A–J)

Ten scenarios were walked through. Full detail is in the session transcript; the summary is:

| Scenario | Finding | Category |
|----------|---------|----------|
| A — Two years of silence | Bob cannot verify Alice's current state | Fixed by 2.1 |
| B — Five years of rendezvous churn | Discovery impossible; out-of-band required | Documented limitation |
| C — Ten years of key rotation | Chain too long to download | Mitigated by 2.1 + chain compression TODO |
| D — Post-quantum migration | Stale anchors cannot authorize new roots | Documented limitation; V2 concern |
| E — Backup from six months ago | Rollback may be rejected by peers | Documentation gap; backup policy needed |
| F — Intercontinental latency | Works; wire-level selection unspecified | Offer 1 / Offer 2 |
| G — Hostile networks | Works if TCP/QUIC transports are first-class | Offer 2 |
| H — Revocation disagreement | Eventual consistency; inherent | Documentation addition |
| I — Identity state disagreement | Verifier's decisions are stale | Fixed by 2.2 |
| J — Peer that never comes back | Relationship state persists indefinitely | Documentation addition; decay policy |

**The underlying finding:** The protocol has no state distribution layer. Identity state is assumed to propagate through peer contact, which fails when peers are disconnected.

## 3.2 Second failure-mode round (Scenarios K–O)

Five more scenarios, categorized:

| Scenario | Finding | Category | Treatment |
|----------|---------|----------|-----------|
| K — Split-brain identity | Two valid `IdentityContinuity` from same root | Design limitation | Document as instance of §22; no protocol fix |
| L — Credit pool insolvency | Pool can run negative indefinitely | Operator policy | Document as operator concern |
| M — Relay key rotation | Relay Authority Key rotation not specified | **Real schema gap** | Add `current_relay_authority_key` to `OperatorManifest` |
| N — Pairing shoulder surfing | 6-digit code + confirmation prompt | Documentation gap | Specify confirmation display; no new mechanism |
| O — Selective rendezvous suppression | No client-side comparison | Client behavior | Document multi-rendezvous query pattern |

**Only M requires a schema change.** The rest are documentation additions or limitations that cannot be fixed.

## 3.3 Additional finding — initial relay key discovery

Related to M: how does a peer first learn a relay's Authority Key? The clean answer is: from the operator's manifest, published to a well-known rendezvous. This needs to be specified alongside M's fix.

# 4. Object-model scope (Offer 5) — finalized

The next artifact is a draft of OBJECTS.md §6 covering all object types that are currently underspecified. The scope was clarified:

These have their own domain separator, signature, and stream. Each requires: purpose, signing authority, stream membership, field table, canonical encoding example, test vector, rejection classes.

**Identity stream:**

- `RendezvousManifest`

**Authorization stream:**
- `Grant`
- `Lease`
- `GrantRevocation`
- `LeaseRevocation`

**Reachability stream:**
- `ReachabilityRecord` (with the two new fields from §2.2)

**Service stream:**
- `ServiceRecord`

**Operator:**
- `OperatorManifest` (adds `serves_identity_state` and `current_relay_authority_key`)

**Commercial:**
- `CreditReceipt` (needs a stream; proposed `stream:credit:{operator_id}`)

## 4.2 Sub-objects

These are fields inside other objects, no separate signature. They need: purpose, field table, encoding rules.

- `Endpoint` (inside `ReachabilityRecord`; carries its own `transport` field)
- `Transport` (inside `Endpoint`)
- `RendezvousEntry` (inside `RendezvousManifest`)

## 4.3 Corrections to the earlier draft plan

Several corrections were agreed before the draft is produced:

1. **`observed_at` as "monotonic time at publisher" is wrong** — monotonic time is verifier-local. Either rename to `issued_at` with wall-clock semantics, or drop it (since `published_at` already serves the purpose).

2. **`endpoint` should be `endpoints`** — a `set<Endpoint>`, sorted by canonical encoding, so multiple endpoints per record are supported.

3. **`transport` belongs in `Endpoint`**, not as a sibling field.

4. **`serves_identity_state` belongs on `OperatorManifest`**, not `RendezvousManifest`. The operator makes the claim about their own capabilities.

5. **`CreditReceipt` needs a stream** if it's a signed object. Proposed: `stream:credit:{operator_id}`, sequenced by the operator.

## 4.4 What stays out of Offer 5

- Wire protocols (Offer 1)
- NAT traversal candidates (Offer 2)
- Push-based revocation (design principle violation)
- `IdentitySnapshot` (redundant with `IdentityContinuity` + rendezvous scope)
- `RelationshipState` decay fields (verifier local state, not objects)

## 6.4 Design decisions still open

Three items are flagged for decision:

1. **Revocation effect on active sessions.** Does revoking a grant terminate an active session immediately, or allow it to continue until the next authorization check? The current design implies the latter, but it should be explicit.

2. **Lease renewal semantics.** How does renewal handle concurrent attempts, and how do in-flight leases interact with new ones? Not specified.

3. **Relationship decay policy.** Should peers prune relationship state after a defined idle period? If yes, what's the default and how is the user warned? Not specified.

These are design decisions, not documentation additions. They should be made before the archive is published.

# 7. What this session clarified about the archive

The session confirmed a structural observation: **the archive is an object model without operational protocols.** The objects exist, but the protocols for how they are used over the wire (publish, fetch, exchange, rotate, migrate) are largely missing. Offer 5 fills in the object schemas; Offer 1 fills in the wire protocols.

The session also confirmed a second observation: **many "protocol gaps" are actually limitations that cannot be fixed.** Split-brain identity is the clearest example — no protocol mechanism can distinguish legitimate from attacker-driven root transitions. The design's correct response is to name the limitation, not to invent a mechanism.

This distinction should guide future review. Every proposed gap should be categorized as:

- **Schema gap** — the object model is incomplete (fixed in Offer 5)
- **Wire gap** — the protocol for using objects is missing (fixed in Offer 1, 2, 3)
- **Documentation gap** — the design says or implies the answer, but doesn't state it (fixed in a documentation pass)
- **Design limitation** — no protocol mechanism can address it (documented and accepted)

Treating limitations as gaps is a common failure mode in design review. It leads to inventing mechanisms for problems that don't have solutions, which makes the design more complex without making it more correct.
